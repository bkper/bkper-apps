# Bkper App Standards

This section contains reusable architecture and quality guidance. It is editable, but preserve it by default and change it only when explicitly requested. Never replace this file wholesale merely to specialize the app. Preserve both guidance marker pairs and maintain the app-specific section as the app evolves.

Follow the Bkper App Quality Guidelines, indexed as `apps/quality.md`, when implementing, refactoring, or reviewing this app.

## Architecture principles

This template is intentionally opinionated. It should be enough to bootstrap an app and provide a strong basis for growing it.

Treat the app API as a first-class product surface:

- Expose reusable app behavior through typed `/api/v1/*` routes whenever it may be used by more than one caller.
- The shipped web client is only one consumer of the API; scripts, external clients, and agents should be able to call the same routes.
- Keep business behavior in `server/src/services/` and expose it through thin routes in `server/src/api/routes.ts`.
- Keep route contracts in `server/src/api/schemas.ts` and document them through the generated OpenAPI spec at `/openapi.json`.
- Keep Lit components focused on rendering and user intent. Do not hide app behavior only in UI components.
- Prefer adding meaning with typed request/response schemas and properties before adding new structural layers.

When adding API behavior, update the server schema and route, add or update unit tests, regenerate the typed client API types with `npm run api`, and intentionally update the OpenAPI snapshot when the public contract changes.

Keep `README.md` focused on end users because it appears on the app listing. Include concise API access details when relevant, but keep development setup, architecture, source control, and compatibility rules in `AGENTS.md` or internal documentation.

## Authentication

Do not implement custom OAuth flows, redirect handling, or token refresh.

| Context               | Pattern                                                                                                               | Location                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Web client direct API | `@bkper/web-auth` provides the token and refresh operation configured in `bkper-js`                                   | `client/src/auth/auth-session.ts`, `client/src/services/book-service.ts` |
| Client app API calls  | The typed API client uses `auth.authenticatedFetch()`; other callers send `Authorization: Bearer <token>` to `/api/v1/*` | `client/src/api/app-api.ts`       |
| Server API routes     | Platform validates bearer auth and injects auth for server-side `new Bkper()` calls                                    | `server/src/api/routes.ts`        |
| Event handlers        | Platform routes `/events`; handler uses `new Bkper()` with outbound auth injection                                    | `server/src/events/routes.ts`     |
| Local dev             | Vite client auth and local outbound both use your CLI credentials (`bkper auth login`)                                | `client/vite.config.ts`, `bkper app dev` |

## Project structure

The root package orchestrates install, dev, test, build, and deploy. Keep browser UI dependencies in `client/package.json`, Worker dependencies in `server/package.json`, and root dependencies limited to cross-package tooling such as the Bkper CLI, Miniflare, and OpenAPI generation.

Keep components focused on rendering and user intent. Register only the Web Awesome components used by the app in `web-awesome.ts`, and style with `@bkper/web-design` tokens. Put auth mechanics in `auth/` and Bkper/client API calls in `services/` and `api/`. Keep shared client state in stores under `state/`, as the Client state guidelines describe: `route.ts` alone reads and writes the URL's path, query, and history, and `app-state.ts` creates and wires the stores. Co-locate each component's view and CSS in one component folder; keep simple presentational components in one file.

Keep server route handlers thin. Put API shape and validation in `api/`, event transport concerns in `events/`, and business behavior in `services/`.

## API contract

The app's public API lives under `/api/v1/*` and is documented at `/openapi.json`.

| Concern                    | File                                      |
| -------------------------- | ----------------------------------------- |
| OpenAPI document metadata  | `server/src/api/openapi.ts`               |
| Request/response schemas   | `server/src/api/schemas.ts`               |
| API route definitions      | `server/src/api/routes.ts`                |
| Server business behavior   | `server/src/services/`                    |
| Generated client types     | `client/src/api/generated/types.d.ts`     |
| Shipped web client wrapper | `client/src/api/app-api.ts`               |

Design API operations around the app's domain behavior, not around the current UI. The UI should call the same routes that another authenticated client could call.

When an app API exposes a Bkper REST API payload, reference its canonical `bkper.*` type through `x-typescript-type`; do not recreate Bkper API interfaces locally. Follow `BookSchema` in `server/src/api/schemas.ts`. This bridge provides compile-time types only, so request bodies still require concrete Zod validation.

API evolution rules:

- `/openapi.json` is the single canonical public contract. It may contain multiple API versions over time.
- Keep `/api/v1/*` and its existing schema names stable once clients may depend on them.
- Do not rename or version schemas just for additive changes. Old generated clients should keep working until they explicitly upgrade.
- Safe changes are additive: new routes, new optional request fields, and new optional response fields.
- Breaking changes include removing or renaming fields, changing field types or meaning, changing route semantics, narrowing accepted input, or making optional inputs required.
- Put breaking changes in a new namespace such as `/api/v2/*`; do not mutate existing `v1` contracts.
- Add new versioned schemas only when a breaking payload shape is needed. Keep the old schema available for old routes.
- Mark old operations with OpenAPI `deprecated: true` only after a migration path exists.
- The committed contract snapshot is `server/test/api/openapi.snapshot.json`; update it only after reviewing the API change.

Agent API change checklist:

1. Classify the requested API change before editing code: additive or breaking.
2. If additive, keep the existing API version and schema names; update routes, schemas, tests, generated client types, and the OpenAPI snapshot.
3. If breaking, add a new API version such as `/api/v2/*`; preserve the old route handlers and schemas for existing clients.
4. Never remove, rename, or tighten a published `v1` field or route unless the user explicitly asks to break compatibility.

Authentication for `/api/v1/*` callers is always bearer-token based:

```http
Authorization: Bearer <bkper-oauth-token>
```

Inside server API routes, do not read or forward that token manually. Use server-side `new Bkper()` and let the platform validate inbound auth and inject outbound auth for Bkper API calls.

# Report

## Overview

Report turns a short request, in any language, or a Bkper query, into a financial report of a Book. The web client and the Bkper Agent call the same app API.

- **Client**: Lit + Web Awesome Pro; a Book picker and, for the selected Book, one input whose report builds as the person types, with the Book and the request in the URL as `?book=<bookId>&q=<request>`, and, in a Book, the report's state (`&state=`, see Report state) and the query the Book shows, which the report follows (`&bookQuery=`, see Web client).
- **Server**: Hono Worker serving typed OpenAPI `/api/v1/*` routes. No `/events`: financial reporting only reads Books. The saved-prompt shelf writes only Book-scoped app metadata, never Book resources. `/report` computes; `/prompts` persists original requests. Both the web client and other authenticated callers use these same service-backed routes.
- **Shared** (`shared/`, package `report-shared`): the report catalog, the strings, bidirectional text and the Bkper languages, imported by both the server and the renderers. It holds only environment-neutral code (no DOM, Worker or Bkper SDK), so browser bundles never pull server code.

## Accounting rules

- Numbers come only from deterministic code over Bkper balances. AI may choose among options the code offers; it never computes amounts or dates, and never writes queries.
- Read-only on Books: never create, update or delete Book resources, and do not subscribe to events. The sole persistence exception is the explicitly requested saved-prompt shelf in app KV (original prompt text only); it never writes to a Book, its executable saved queries or its financial data. Normal report computation remains read-only.
- Periods are whole months of the Book's calendar, written into the report's Bkper query by `period-query.ts` (see Period queries) and resolved by Bkper from the Book's today in its time zone; the query read is the query shown and opened in Bkper. A request that names no period reads activity (Incoming, Outgoing) for this year, positions (Asset, Liability) today, and a trend over the last 12 months; only when the report's own answers then have no movements does it read one query of its history and the last year that has them instead (`default-period.ts`, see Default period), so Books with old data still show their data. A running period (this month, quarter and year, year to date, the last 12 months, all time, or a written period that contains the current month) reads through the end of the current month, so it includes transactions dated later this month; activity today reads the current month. Past periods are whole calendar periods. A comparison covers the same months: a whole period compares with the previous month, quarter or year; a running one with the same months of the previous period (this quarter in November, October and November, with July and August). A position is read at the end of its period, a balance now (today, or a running period) at `before:$d+1`, the only day a report reads; it compares with the end of the previous period's same months (for today, the end of last month). An intent with `compareWith: 'year_earlier'` compares instead with the same months a year earlier, and a position with the end of the same month a year earlier; for a year it is the previous period. An intent with `compared` parts compares with the period they name ("last year vs 2023", "Q3 vs Q1"), of the same kind; one that cannot be made (another kind of period, one that overlaps, or anything with all time) compares with the previous period instead (all time with nothing) and says so (see Period queries). All time has no comparison.

## Book snapshot

The snapshot is the Book's map (`server/src/services/snapshot.ts`), loaded by `snapshot-loader.ts`: group and account names, the hierarchy and natures, and which accounts have transactions posted (`posted`, the payload's `hasTransactionPosted`): the Book's structure alone, from which Jev's root options, names, net results, suggestions and the Book's problems (see Book problems) are chosen. It holds no amounts and no dates of movements, and never supplies a shown amount.

- One `bkper.getBook(id, true, true)` call, and no balances query: the map's cost does not grow with the Book's history or its number of root groups (Aqua Tecnologia S/A, 128 roots and 1,404 accounts: about 0.3–0.6 s, where one query per root took 7–55 s).
- Root groups are in Book order, the order of the Book's payload (which Bkper does not keep stable between loads: groups created together can swap). Subgroups come under their parents and accounts under the groups each lists, by name ignoring case (`byName`), as Bkper lists them in balances. Accounts appear once even when several roots contain them; archived accounts are in the map, marked `archived`.
- Accounts in no group are apart (`ungrouped`), with their natures: no root's query reads them.
- KV caches a snapshot for 60 s per user and Book (`snapshot:v7:<userId>:<bookId>`; `v1` held amounts, `v2` lacked the accounts in no group, `v3` held the months with movements, `v4` lacked `posted`, `v5` the Book's date format, `datePattern`, in which Bkper writes the dates it read, `v6` the groups the Book hides, `hidden`). Identifying the user (`currentUserId`) costs one `getUser` call per request; the balances cache needs it too. `Server-Timing` reports `user`, `kv` and `book` (loading the map); the per-request `ServerTiming` lives in `AppContext`.

`npx tsx scripts/verify-snapshot.ts [--today=YYYY-MM-DD] <bookId>...` checks snapshots of live Books, read-only, with your `bkper auth token`: cold and warm load times, that loading asks no balances query, and the roots, the subgroups and accounts under each group by name, every group's name, nature, parent, subgroups and accounts (archived too), every account's name and nature, and the accounts in no group against `bkper group list`/`bkper account list`. `--today` reads a Book as of an earlier day.

## Book problems

`server/src/services/book-problems.ts` finds, by fixed rules from the map (no balances, no AI), what keeps a Book from having the report asked for, in this order: `empty_book` (no account has transactions posted), `nothing_to_report` (no root groups, or more than half of the accounts with transactions posted are in no group; exactly half is fine), `no_net_result` (a net result asked for that `netResultOf` cannot give, including activity roots that share accounts) and `mixed_group` (a group read whole, the subject or one side by side, whose accounts with transactions posted, at any depth, hold both permanent and non-permanent ones; Asset with Liability, or Incoming with Outgoing, is fine; an account target is never mixed). The first two are of the whole Book (`bookProblem`): `createReport` rejects every request with them before Jev or any query (`assertReportable`), and `/suggestions` returns them as `problem` with no suggestions and no query (`readOpening`). The other two are rejected when the report is planned, before any query (`planReport`). Each is a `ReportError` whose reason is the code, carrying the `BookProblem`: the Book's name, `canOrganize` (OWNER or EDITOR, from the map's permission), and what is involved (`ungrouped` and `total`; `incoming`, `outgoing` and `shared` root names in Book order; the `group` name). Request errors (`not_a_report`, `future_period`, …) and flat but valid Books are no problems.

## Agent links

The web client says what keeps a Book from its reports and, to whoever may fix it, offers the Bkper Agent with a request ready (`client/src/agent-link.ts`, `AppState.agentLink` and `openAgent`, drawn by `report-page-view.ts`). A Book problem (see Book problems) replaces any notice with its message (`problem_*`): `empty_book` and `nothing_to_report` when the Book opens (from `/suggestions`), `no_net_result` and `mixed_group` on the request that hits them, until the next request.

- **Role.** The action shows only when the problem's `canOrganize` is true: the Book's permission is OWNER or EDITOR, from the snapshot the server already loaded, with no request of its own. Others read `problem_ask_owner` (`problem_ask_owner_start` for an empty Book) and get no link. It is a hint: the Agent and Bkper check the person's permissions on every change.
- **Link.** `<Bkper origin>/books/<bookId>/transactions?app=bkper-agent&q=<request>` (`agentUrl`), the Book's transactions with the Agent open. `q` means nothing without `app=bkper-agent`, so it never mixes with the Book's `query`. The Agent reads exactly one `q` value, plain text, trimmed, of 1 to 2,000 characters; any other (missing, empty, repeated or longer) it leaves out whole, never truncated, since a cut request could change its meaning. It opens a new session with the text in its input and never sends it automatically: the Agent can change Books, so the person reads it and sends it. It removes `q` from the address once read (standalone, only after sign-in), and later Agent URLs never carry it. Contract documented publicly for people (`https://bkper.com/docs/ai/bkper-agent/prompt-links`) and App developers (`https://bkper.com/docs/platform/apps/context-menu#opening-bkper-agent-with-a-prompt`).
- **Request.** A fixed template in the interface's language, never AI (`agentPrompt`, `agent_prompt_*`): in the person's voice, naming the Book and what is involved (root names as `Intl.ListFormat` lists, counts with `Intl.NumberFormat`), asking to organize groups, and ending with groups only, not transactions. Translations keep that voice, the placeholders and the quotes around `{book}`. `empty_book` opens the Agent with no `q`, so its own start takes over; a request longer than `MAX_AGENT_PROMPT` (2,000) also goes without one rather than be left out by the Agent.
- **Opening.** In a Book whose last `bkper:host-ready` lists `navigate`, a plain click sends one `bkper:navigate { url }` to that origin only (`BookHost.navigate`, for a URL on it), and the Book keeps the target's `app=bkper-agent` instead of reopening Report; before that, or for a modified click, the link opens in a new tab. Standalone, it is a plain link in the same tab. The link is always on `https://bkper.app` (`PRODUCTION_BKPER_ORIGIN`), even from the preview app: Bkper in production opens the preview (`menuUrlDev`) for the app's developers, so the app's origin never tells which Bkper is around.
- Bkper hosts must read `q` and keep `app=bkper-agent` on `navigate` before this ships; an older host opens Report again or an empty Agent.

`npx tsx scripts/verify-book-problems.ts [--screenshots=<dir>]` checks the messages and the action in the real client (Vite client required; the API stubbed, no Book, Worker or KV read), in an expanded Book panel and standalone, at 1100 and 390 px, light and dark, in English: each problem on opening or on its request shows one message; OWNER or EDITOR get the action with its label and exact link (no `q` for an empty Book), a VIEWER none and the ask-the-owner text; the action fits the narrowest panel; in the Book a click sends exactly one `bkper:navigate` to the Agent's URL and leaves the panel in place; standalone it opens the same URL in the same tab; nothing logs an error. It writes a screenshot per scenario to `/tmp/report-book-problems`. It plays the Book from a stub: it does not prove that the real Book or Agent read `q`.

## Default period

A request that names no period (or whose period Jev is unsure of) gets the default one from `resolveIntent`, marked `defaultPeriod`: this year for activity, today for a position, the last 12 months for a trend. `readReport` (`default-period.ts`) reads the report's own queries; only when the period is this year or the last 12 months and those answers have no movements for the report's groups and accounts (an amount in a month of the period, for them or anything Bkper lists under them; a month whose movements all net to zero shows nothing and counts as none) does it run ONE more query, `historyQuery`: the group its first subject is read from (the intent's own root, or its target's group, see Report balances), `<group filter> [#tags] before:$m+1 by:m` (all time's activity, through the current month), never several groups at once and never one per group. From its last month with movements, `defaultPeriod` gives that year (or keeps the period when it moved within it), and the report of that year is read with its own queries; every amount still comes from them. A position today never moves. An intent always names its period and reads it as named; the suggestions' intents, built for their texts, already carry the period this rule gives (see API).

## Period queries

`server/src/services/period-query.ts` builds the date part of a report's Bkper query from the parts of a period a request names, so the query, not the app's calendar code, holds a report's dates. Reports use it end to end: an intent holds its period as these parts (`period`, `compared`, `compareWith`; the parts and their translation from period ids live in `report-shared/report-intent`), and `planReport` builds the date part of every query (the period's, its comparison's and the history's) with `buildPeriodQuery`. A `comparisonError` is never silent: `reportPeriod` reads the default comparison instead (the previous period, all time none) and keeps the error, which the report data (`comparisonError`), the Worker's report trace (`trace.comparisonError`) and the spec's `Report` `notice` (`notice_comparison_fallback` naming the period compared with instead, `notice_comparison_none` for all time) carry. A report's labels say what Bkper read (see Period labels).

- Parts are plain JSON (`PeriodRequest`): `period` `{ span?, year?, month?, quarter? }` (`span` one of `PERIOD_SPANS`; `year` `current`, `previous`, `before_previous` or a written year; `month` 1–12, `current` or `previous`; `quarter` 1–4, `current` or `previous`; left out is unspecified), optional `compared` `{ year?, month?, quarter? }`, and `compareWith`. `periodRequestOf(id, compareWith?)` translates every period id of older intents (`today`, `this_year`, `2025-Q3`, …): relative ids into relative parts, dated ids into fixed ones; `periodIdOf` is its inverse; `intentWithParts` (and the server's `reportIntentOf`) gives an intent of either form with parts.
- `buildPeriodQuery(request, { today, nature })` gives the dates of the period and of its comparison (`dates`, ending with `by:m`, with `kind`, `running`, `first` and `last` months), or `unspecified_period` / `future_period`. A month or quarter with no year is the latest that has started; the current or previous month or quarter in a relative year is as many years away, and in a written year is its own month of that year (last month, asked in January, with 2024 is December 2024). Compared parts left out are the period's; a named month or quarter neither gives a year to is the latest before the period. Without compared parts: the previous period, or with `year_earlier` the same months a year earlier. A comparison wholly later than the period swaps with it ("2016 vs 2018" reads 2018 against 2016, "last year compared with this year" this year to date against the same months of last year; a person comparing two periods wants both, and change reads from the earlier to the later), so the later one is the period, cut at the current month when running, and `future_period` when it has not started. A comparison of another kind, or overlapping the period, is `comparisonError` (`comparison_kind_mismatch`, `comparison_not_earlier`; all time `comparison_unavailable`), never replaced by another.
- Whole months only. Bare variables (`$y±n`, `$m±n`) for periods relative to today on their own (`on:$y-1`, `after:$y before:$m+1`, `on:$m-12`); ISO `yyyy` or `yyyy-mm` for written years, named months and every quarter. Never a full date (Bkper then reads by day), a variable combined with a month (Bkper reads the whole year), or a month offset for a named month. A running period reads through the end of the current month and its comparison the same months; a position reads the end of its period, `before:$d+1` when running.
- `resolveQueryDates(dates, today)` resolves those forms into months as Bkper does (and the day of `before:$d+1`), and throws for any other. Bkper's own `previousRange` is not used (see the known issues below).

Known Bkper issues:

- `previousRange` is wrong for mixed ranges: `after:$y before:$d+1` gives `after:2027 before:11/11/2026`; the builder computes comparisons itself.
- A variable combined with a month (`01/$y-1`, `$y-1/01`, `$y-1-01`) is silently read as the whole year (`01/$y-1` reads nothing in year-first Books); the builder never writes one.

`npx tsx scripts/verify-period-queries.ts [--day-first=<bookId>] [--month-first=<bookId>] [--year-first=<bookId>]` checks, read-only with your `bkper auth token`, that Bkper reads every kind of query the builder writes as `resolveQueryDates` does, in each Book date format (`dd/MM/yyyy`, `MM/dd/yyyy`, `yyyy/MM/dd`). For each format it takes the flag's Book, else a known test Book (Nimbus, `1.AAQ Services, Inc`, `Copy from Bkper Tax Bot` or `DEMO Expense Reports`), else the first of your Books in that format with an unmixed Incoming or Outgoing root and an unmixed Asset or Liability root, and names a format it finds no Book for. As of the Book's today in its time zone it builds the samples of `scripts/verify-period-queries/samples.ts` (each span, relative and written years, months and quarters, running periods, the default, year-earlier and named comparisons, activity and positions, a balance now), reads each distinct query on such a root (`before:$d+1 by:m` reads by month only with a group), and compares Bkper's `range`, `rangeBeginLabel` and `rangeEndLabel` (parsed in the Book's date format, `bkper-dates.ts`), `periodicity` and the months of the balances: within a period exactly its months; from the start of the Book, none after the month of `before` (Bkper may list that month itself). It prints a table per Book and exits non-zero on any mismatch or balances by day. On 2026-11-09 it passed on Nimbus, `1.AAQ Services, Inc` and `DEMO Expense Reports` (`Copy from Bkper Tax Bot` has only mixed roots), 56 queries each.

## Period labels

A report's subtitle, its comparison (`vs. …`) and the legend of a compared chart name the days each side's query actually read, in a form chosen by the kind of period asked for, as Bkper labels its answer (`rangeBeginLabel` and `rangeEndLabel`), never the app's own calendar: `readDays` (`server/src/services/bkper-dates.ts`) parses them in the Book's date format (`dd/MM/yyyy`, `MM/dd/yyyy` or `yyyy/MM/dd`, the snapshot's `datePattern`) into `ReportBase.period` and `previous` (`after`, none from the start of the Book, and `before`). An answer without labels in that format (an unknown format, or a balance cached before they were kept) reads the days its dates resolve to as Bkper resolves them (`resolveQueryDates`). Every source of a report has the same dates, so the first source's answers name them. `Labels` (`report-spec.ts`) words them with `Intl` in the report's language, both sides in the same form (`ReportBase.period.kind`, the span asked for, with the months each side read):

- whole months: a whole period of the kind asked for by its name, a year (`2025`; also the year to date in December), a quarter (`period_quarter`, `Q3 2024`, its year in plain digits) or a month (`January 2025`; also activity now); a running or partial one, or a span with no name (the last 12 months), by its short month range (this year in March `Jan – Mar 2026` against `Jan – Mar 2025`; this quarter in November `Oct – Nov 2026`; `Dec 2025 – Nov 2026`), never a relative word. When either side is not a whole period of the kind, both are ranges;
- a position: `position_as_of` with the last day read (`As of Nov 9, 2026` now, `As of Oct 31, 2026` at a month's end), compared with that day (`vs. Oct 31, 2026`), and both legends `As of …`;
- all time: `period_all`, with the Source's dates from the first month of data.

The Source's period of an activity is its exact days (`Oct 1 – 31, 2026`).

## Request text

The text that stands for a report keeps what was asked: the response's `text` (for every request, a prompt's too; of a Bkper query, the query itself, see Query reports), which a report's state holds (see Report state), is the spec's `Report` `request` (`report-shared/report-text`, `reportText`, which falls back to the title and subtitle for specs written before), built by `requestText` (`server/src/services/request-text.ts`; `periodTexts` gives its two sides) from the intent's parts in the report's language: its title (`request_by_month` around it when the report is by month), then its period, then `request_versus` with what it is compared with, then its hashtag (`#tag`), so a person can edit it and ask again, and sent back as a prompt it asks for the same report. Names stay apart from the letters a list or a phrase joins to them (Arabic `و`, Thai `และ`), so the request finds each name side by side. Relative parts stay relative words (`Intl.RelativeTimeFormat`: this year, last quarter, now; strings for year to date, the last 12 months, all time, a quarter without a year and a period in a year, such as January last year), written ones as written (`Expenses Q3 2024 vs. Q1 2024`), and this year adds no words where the period already means it (`Expenses year to date`, never `year to date this year`). A quarter is written as a person types it (`request_quarter`, `request_quarter_in_year`: `3º trimestre 2024` in Portuguese, where Jev does not read `T3` as a quarter), and year to date in another year has its own string (`request_year_to_date_in_year`), so no language repeats the word year. What it is compared with: its own parts, those equal to the period's said once; a comparison that names only another year is said relative to the period where the period's month, quarter or months are relative (`last month vs. the same month last year`, `this quarter vs. the same quarter 2023`, `year to date vs. the same months last year`, `request_same_*`; a balance now `vs. 1 year ago`), else whole (`Expenses January vs. January 2019`, `last year vs. 2023`); `year_earlier` of a period in a written year or last year names the year before (`Q3 2016 vs. Q3 2015`, since Jev reads "a year earlier" as last year), else `request_year_earlier`; a named month or quarter in no year compared with itself is the one a year earlier; and a comparison that would read as the period itself is left out, so the two sides are never the same words. Suggestion chips follow the same rule (this year, or the written year the default moved to). `server/test/services/request-text.test.ts` writes every combination of parts the builder accepts (`server/test/fixtures/period-combinations.ts`, span × year × month × quarter × compared parts or `year_earlier`) in English, Portuguese, Spanish, Japanese and Arabic, and checks that the sides differ and no phrase repeats itself next to itself. Compositions of `Intl` words with older strings still repeat in some languages whose ICU data is thin or whose words reduplicate (such as `-2 y` in Bambara, Malay's last quarter followed by last year, Mizo's all time, a quarter's number before 2 years ago in Persian or Thai); the new strings repeat in none.

`npx tsx scripts/eval-periods/read-back.ts [--set=combinations|cases] [--languages=en,pt,es,ja,ar] [--today=2026-11-09] [--cases=<run.json>] [--mismatched] [--dry-run]` asks real Jev to read the request texts back (Personal finances' snapshot, read-only; Jev with `BKPER_AI_TOKEN` or your `bkper auth token`) and scores the months of the period and of its comparison as `eval-periods` does: `combinations` (the default) one combination per kind of English text of those an exact reader of the parts reads back (`readPeriod` reads some parts its own way, such as a relative year with the last 12 months), leaving out comparisons of another kind unless `--mismatched`; `cases` each period the period evaluation's requests mean. Each run is written to `/tmp`; `--cases=<run.json>` asks the same combinations again, to compare wordings. On 2026-11-09, at that today (cached Bkper AI answers for unchanged texts): `cases` read back 434 of 435 (87 periods × 5 languages; the miss: Spanish all time vs. last year, read as no period), where the previous wording read 416 (Portuguese and Spanish quarters written `T3`, and all time vs. all time); `combinations` 1,486 of 1,915 (383 kinds × 5 languages; en 314, pt 293, es 311, ja 266, ar 302), where the previous wording read 1,390, better in every language (110 texts better, 14 worse); its misses are mostly unnatural combinations, such as a relative month in another year compared with another relative month (`this month last year`, which Jev also reads as compared a year earlier), Japanese `前四半期`, and year to date in another year in Portuguese, Japanese and Arabic, which Jev reads as the whole year. Earlier, measured once, the previous wording read 186 of 187 texts of 17 kinds of parts in 11 languages. `request_versus` uses a connective, not a postposition, so "last year vs. 2023" is not read as 2023.

`npx tsx scripts/eval-round-trip.ts [--books=nimbus,personal,rosalia,aqua] [--languages=en,pt,es,ja,ar] [--only=<n>,...] [--dry-run]` checks the round trip of a report's own text on real Jev, read-only (maps and balances with your `bkper auth token`, the app's balances loader; Jev with `BKPER_AI_TOKEN` or the same token): for each test Book it builds reports by intent from the map (its suggestions; an activity root in relative and written periods, compared with named periods and a year earlier, by month, with a hashtag; a position root now and at past ends; a subgroup and accounts; targets side by side; the net result), in each language, sends each response's `text` back as the only thing in a prompt, and compares the two reports (`scripts/eval-round-trip/identity.ts`): the groups and accounts the query reads, the hashtag, the months of the period and of its comparison, by month and view, and the language; the chart, a request option, is left out. It prints each miss with both reports and Jev's judgments, and writes the run to `/tmp`; `--dry-run` prints the texts and sends none back. A text that does not round-trip is written more clearly here, never stored.

## Period questions

`server/src/services/period-questions.ts` reads a request's period as small judgments of Jev, in the app's one decision request (`buildIntentRequest` asks them after its other questions), for the parts of `period-query.ts`. Every question, criterion and threshold of the period lives there, `year_earlier` too.

- Seven choices about the state `{ request, today }`: `span` (`month`, `quarter`, `year`, `year_to_date`, `last_12_months`, `all_time`, `now`, `unspecified`), `year` (`this_year`, `last_year`, `year_before_last`, `next_year`, the years the request writes, `unspecified`), `month` (January … December, `this_month`, `last_month`, `next_month`, `unspecified`), `quarter` (Q1 … Q4, `this_quarter`, `last_quarter`, `next_quarter`, `unspecified`), and `compared_year`, `compared_month` and `compared_quarter`, the same options for a second period the request compares with. The period questions answer for the first period a request names. No option holds a date of its own, so the questions never go stale: the years are found by code (`findWrittenYears`: runs of exactly four digits in ASCII, Arabic-Indic, Extended Arabic-Indic, Devanagari or full-width digits, 1900–2199, at most 12), and no criterion holds a year. The relative options carry examples in several languages, among them the words `Intl.RelativeTimeFormat` writes in request texts (such as `前四半期`, `الربع الأخير`, `अंतिम तिमाही` and `bu çeyrek`), so a request text reads back as written. `year_earlier` (`YEAR_EARLIER_QUESTION`) is a yes or no among the intent's, where it always was in the request.
- `readPeriod(answers)` is pure: each part the model is sure of (`PERIOD_THRESHOLDS`: 0.5 for the period's own parts, 0.6 for a second period's, whose mistake compares with the wrong months while none falls back to the previous period). A sure next year, month or quarter, for either period, is a period that has not started: no parts, `reason: 'future_period'` (compared with an earlier period the two would swap and read it anyway), which the resolver answers as `ReportError` `future_period`. Otherwise the rules of `PERIOD_RULES` apply, in order: `span_alone` (a month, quarter or year with nothing saying which, such as monthly spending, is no period), `rolling_period` (the last 12 months ignore a relative year, said for the comparison), `kind_of_period` (a second period said as a month and a quarter is of the period's kind: Q2 read as June too), `same_as_period` (compared parts equal to the period's say no other period, so "January 2016 vs the same month a year before" reads `year_earlier`), and `previous_of_period` (the previous month or quarter of a second period with no year is the default comparison; last year, or the year before last, counts back from a written year: "2016 versus last year" is 2015). No sure part of the period's own is no period (the default). Without compared parts, `year_earlier` compares with the same months a year earlier. The trace holds each judgment's answer, score and the value read (`next` for the next year, month or quarter), and the rules that fired.

## Report balances

Every amount a report shows is a Bkper balance of one group or account, read from the response to one of the report's own queries, with the sign Bkper shows in its charts (bkper-js representative balances: negated for debit nature). Report never adds or subtracts amounts across groups or accounts and never changes a sign by nature; the one exception is a net result it calculates (see Report calculation). Amounts stay decimal strings; compute with bkper-js `Amount`, never binary floats.

- `planReport(intent, snapshot)` (`report.ts`) names the queries: for each group a report reads from (`sources`: the root, a target's group, or each root of a net result Report calculates; never several groups in one query), one of the period, `group:'<group>' [#tags] <dates>`, and one of the period it compares with (the same months of the previous period, or a year earlier) the same way, run in parallel (`planQueries`); `<dates>` is the builder's (see Period queries), so every query ends with `by:m`. A period that has not started is `ReportError` `future_period`.
- A report's subject (`ReportSubject`) is the node it is of, a net result Report calculates, or targets side by side. The intent's optional `target` (an id) is a group or account under its root group, at any depth, and the report reads it from one group's queries (`sourceOf`), derived from the map, never stored: a group target from its own (`group:'<target>' …`, period-scoped like a root's); an account from those of the smallest group it belongs to, the one with the fewest groups and accounts at any depth, the first in Book order (roots in order, each with its subgroups) on a tie, and from that response by name. Accounts can belong to several groups; whichever root the intent names, an account reads the same group, so its root (kept for the state's meaning) does not change what is queried. Never `account:'<name>'` for an account in a group, which Bkper does not find for some names (see below). A root's query is no longer read for a target: on Aqua Tecnologia S/A, whose `Balanço Patrimonial` holds 1,070 accounts directly, its accounts read groups of 2 to 883 (`Contas a receber`, the smallest group of 866 of them). An account in no group is a root of its own (`root` is its id, with no target), read with `account:'<name>' …`. A target with `net-result`, with an account root, equal to its root, or not under it is `ReportError` `unknown_target`, before any query; an account in a group as `root` stays `unknown_root`. The nature (position or activity) is the subject's own, a target's rather than its root's.
- Targets side by side (`alongside`: more `{ root, target? }` after the intent's own `root` and `target`, at most `MAX_ALONGSIDE` (5)): each is checked exactly as a single subject (a root, an account in no group, or a target under its root; `net-result` among them is `unknown_target`), the same group or account asked for again (even under another root) is shown once, in the order asked for, and one left alone is that subject's own report. All must be positions or all activity, else `ReportError` `mixed_targets` (API 422), before any query. The plan reads each distinct group's queries once, in parallel, the same each target reads alone: targets share a query only when they are read from the same group, and each is read from its group's responses. "A and B" and "A versus B" are the same report.
- Bkper answers a query of an account it does not find by its name with no balances at all: in some older Books (Nimbus, Personal finances), `account:'<name with spaces>'` finds nothing, in balances and in transaction search alike (bkper-core `BookEntity.getAccountIdsMap` looks a single name up by the account's stored normalized name, which seems older there). Group responses are unaffected, so targets under a root, read from a group's response, read correctly; an account in no group that is not archived and is missing from its own answer is `MissingBalancesError` (API 502 `upstream_error`), never a zero. A report's link to Bkper for an account (`account:'<name>'`) is Bkper's own query and shares that limit.
- Activity reads a node's period balance (the total) and its monthly period balances (a month without a bucket had none); a position reads its top-level cumulative balance at `before` (never a month's bucket) and, by month, the cumulative balance of the month's bucket or of the last one before it (Bkper leaves out months after the last movement). Months are never added up into totals. The months a report shows are the builder's `first` to `last`: Bkper also answers the month of `before:` in a query without `after:`, which is left out. A balance as of a day (`now`, or the end of a month) shows instead the 12 month-ends ending at its day (`BALANCE_LINE_MONTHS`), so its line shows the year that led to it, from the same query: a position reads with no `after:`, so its monthly buckets reach back to the Book's start, and no other query is read. The last point, the cumulative of the day's month bucket, is the headline (top-level cumulative at `before`); the headline, rows and comparison are unchanged. A quarter, a year or the year to date keeps its own months. All time by month runs from the first month (in a plausible year) Bkper answers the report's queries with.
- The hashtag filters every query. A report has at most one (`MAX_HASHTAGS`): Bkper's balances filter by a hashtag only when the query has exactly one (bkper-core `Query.isToFetchTagBalances`); with two or more they ignore them all and answer the unfiltered balances (on Rosália, `group:'Despesas' #supermercado #kitsantantonio` in 2025 answered exactly the balances without hashtags, January -10,667.69, where its transactions with both came to 791.26). A position never reads with `after:`: under `after:`, Bkper's cumulative balance with hashtags starts from the balance of every movement, with the hashtags or not.
- `readQueryBalances` (`balances.ts`) keeps a response's balances by Bkper name, each node's nature (`credit`, `permanent`), and the subgroups and accounts Bkper lists under each group; a node Bkper left out of a response has no balance there (zero). It also keeps the dates Bkper read: `range`, `rangeBeginLabel`, `rangeEndLabel` (in the Book's date format) and `periodicity`, and each balance's year and month.
- `loadBalances` (`balances-loader.ts`) caches each exact query's balances for 60 s in KV per user, Book and the Book's today (`balances:v3:<userId>:<bookId>:<today>:<sha-256 of the query>`, `today` the snapshot's, so a query of relative dates such as `on:$m` is never served for another day; `v2` had no range, `v1` no structure; queries can be longer than a KV key), reads the misses from Bkper in parallel, and stores them in the background. `kv` and `balances` in `Server-Timing` include it. A report's `dataAt` is when its oldest balances were read.

## Report calculation

`buildReport(intent, snapshot, balances)` (`server/src/services/report.ts`) turns an intent and the balances of its planned queries into report data: the answer (amount, previous, change), the months of the period, the main chart and every chart that fits (`charts`), the breakdown tree, type colors, the exact Bkper query and its URL. It is pure and deterministic.

- `root` in the report data is its subject: the root group, the target, the account in no group, the combining group, or `net-result`. A target's report is drawn from the target in the response of the group it is read from: its own balance as the answer, the rows Bkper lists under it (an account has none), its series by month, its name as the title, and `query` (the Source and the link to Bkper) the target's own filter (`group:'<target>'` or `account:'<target>'`, with the hashtags), so the link shows exactly its transactions, whose balance is the one read from its group's response.

- Targets side by side (`targets` in the report data, which is also the `breakdown`; no `root` and no `answer`): each target a row in the order asked for, with its own Bkper balance now, before and by month, and the rows Bkper lists under it (with their shares of it), as in its own report. Nothing adds them up: no total, no share of the targets, nothing calculated. `query` is `(<filter> OR <filter> …) [#tags] <dates>`. Charts are computed by the same rules with `facts.sideBySide`: by month a series per target, `area`, `ranked-bar` (the targets with an amount, ranked by size), `compare` and `table` fit; `donut` and `stacked` never do (`side_by_side`, the charts that imply a whole), nor `waterfall` (`no_bridge`). With no view or chart asked for, ranked bars.
- Roots that are permanent (Asset, Liability, or mixed of both) report a position at the period's `before`; all others, and the net result, report activity within the period.
- A calendar period that contains the current month (`2026`, `2026-Q4`, `2026-11`) reads through the end of the current month, and is labelled by the months it read (`2026` in November as Jan – Nov 2026); activity today reads this month. Periods that have not started are rejected (`ReportError`, `future_period`).
- The breakdown holds only the rows Bkper returns (`RowReader`): the subgroups and accounts each response lists under a group, in either period, each with its own balance as Bkper returns it, so a mixed group's rows need not add up to it. There is no remainder row: a node Bkper leaves out is no row, and one it returns that the map lacks (such as an account archived at zero) is a row, `group:<name>` or `account:<name>`, typed by its nature. Rows without amounts in any period or month are left out; rows are sorted by size, then rows without an amount in the period, which charts leave out. Shares (`child / parent`, display ratios) are left out under mixed parents.
- The net result (`net-result`, `netResultOf`): the root group that combines Incoming and Outgoing accounts (mixed, not permanent), the one with the most accounts, the first in Book order on a tie: its report is that group's, as Bkper calculates it. Else, when every activity root is purely Incoming or purely Outgoing, there are both, and no two share an account (in the map, and again in the responses), `calculatedNetResult` is the one amount Report calculates: Bkper's totals of the Incoming roots minus those of the Outgoing roots (`Amount`), in the period, the previous one and each month (`calculated.months`), with the roots as its rows, Incoming first, a `total` row and a series per root under its line; the spec labels it "Calculated by Report" (`source_calculated`) with a hint to add a combining group. Any other structure has no net result: `ReportError` `no_net_result`, before any balances query (API 422 `no_net_result`, the client's `error_no_net_result`). A Book without activity roots is still `no_activity_roots` (`not_a_report`).
- Every chart that fits is computed (`charts.views`, in `VIEW_KINDS` order: `bar` or `line` by month, one of them, `area`, `stacked`, `ranked-bar`, `donut`, `compare`, and `table`, which always fits, as `{ kind: 'none' }`; so at most six charts, the table aside, which a test checks over every preference), from the same rows and months, so a renderer can switch between them with no new numbers. Each chart's fit is decided by code from the report's facts (`charts.facts`: top-level rows with an amount, how many are negative, whether they are of another type than the root or under a mixed root, months, a previous period, a net result (calculated, or of a mixed activity group), a permanent root, targets side by side), and a chart that does not fit has an `UnfitReason` (`net_result`, `negative_part` with its `rowId`, `mixed_parts`, `few_parts`, `too_many_parts`, `few_months`, `no_amounts`, `no_previous`, `not_a_whole`, `no_bridge`, `side_by_side`; the contract keeps `not_a_bridge` and `no_change`, no longer given). Charts never imply a whole that does not exist: slices and stacked parts must add up to the root's own balance (`not_a_whole`, a comparison of Bkper's amounts that shows no sum).
- The main chart (`chart`, its kind `charts.main`) and the rule that chose it (`charts.rule`): the preference when it fits (`preference`); else the first fitting chart of its `CLOSEST` list (`closest`: `bar` → line, area, ranked bars, donut; `line` → bars, area, ranked bars, donut; `ranked-bar` → by month, donut; `donut` → ranked bars; `stacked` → by month, area, donut, ranked bars; `area` → by month, stacked, donut, ranked bars; `compare` → ranked bars, donut; `waterfall` → compare, ranked bars, donut), else, as for `auto`, the rules (`rules`). A pie asked for is a donut (`shownPreference`), so its kind, `charts.unfit` and the response's `chart.asked` say `donut`. A preference that does not fit is `charts.unfit` (its kind and reason) and marks the main chart `fallback: true`; it is never among the views, and the spec says why in the Report's `notice`.
- Charts by the rules: the named view first; otherwise `monthly` (or the `trend` view) means by month over 2+ months (bars for activity, a line for positions; a net result Report calculates draws a bar series for each of its roots that has an amount, and the net result as a line over them; no chart when every value of every month is zero, as charts leave out rows without amounts), else (also a trend of one month: one point by month is no chart) a breakdown chart over the rows with an amount: a donut for 2–6 positive rows of the root's type, ranked bars otherwise, none for fewer than two; the `breakdown` view (a composition asked for) the same. `total` has no chart.
- The intent's `chart` (`REPORT_CHARTS`) is the person's preference; left out or `auto`, the rules choose, so older intents give the same main chart. `pie` stays in `REPORT_CHARTS` (the request's `chart`, the intent and URL states) so older callers and links keep working, and is drawn as a `donut`. What each chart needs to fit:
  - `bar` (activity) or `line` (positions) by month: 2+ months (a single point by month is never offered), with an amount in any of them; the other of the two only when preferred, from the same series, and then in place of the usual one, never both. `ranked-bar`: 2+ rows with an amount.
  - `donut`: the rows with an amount, 2 to `MAX_DONUT_ROWS` (6), all positive and of the root's type (not under mixed groups or a net result), adding up to the root.
  - `stacked`: a series per top row with an amount in a month, each drawn, for 2+ months, 2 to `MAX_STACKED_PARTS` (6) parts of the root's type (not a net result or a mixed group), adding up to the root in every month.
  - `area`: the series of the chart by month, for 2+ months, when any of them has an amount in a month.
  - `compare`: the rows with an amount now or in the previous period, when there is one (not all time).
  - `waterfall`: never fits (`no_bridge`): its bars would be sums Report makes. It stays in the request's `chart`, the intent, state and catalog contracts, so a request for one says why in the notice, and shows the closest chart (`compare`, ranked bars, donut).
  - `table`: no chart, always.
- Ratios (`change`, `share`) are decimal strings rounded to 4 places; format them, and amounts, only when rendering.

`npx tsx scripts/verify-report.ts [--today=YYYY-MM-DD] [--hashtag=<tag>] [--root=<id or name>] <bookId>...` (`--root`, repeatable, checks only those roots, their targets and default periods, and no net result, for a large Book) reads each root's history by month from the CLI (`bkper balance list`, apart from the app), and builds reports of several intents per root (and the net result) within that data range, and of targets (every subgroup and the two busiest accounts of the year under each root, and the first three active accounts in no group, by month, a quarter, the last month compared and today; with `--hashtag` too), from their own queries, as the Worker runs them, and cross-checks them against `bkper balance list`, read-only: a target against the CLI's query of the target alone (an account under a root against its row in the CLI's query of the root, as the CLI's `account:'<name>'` finds nothing for some accounts of older Books), after checking that it reads the queries of one group only: a group its own, an account a group holding it with none holding it smaller in the map (an account in no group, queries of its own; one Bkper does not find by name is no report, and the CLI finds nothing either); the answer and previous period, and every row at any depth now, before and in every month, each as Bkper's own balance of its group or account, to the cent (exactly, or, for an amount Bkper answers with more digits than a JavaScript number holds, such as Aqua's `631410.608024020000488`, at the precision the CLI prints, `Amount.toNumber()`); that every group or account the CLI lists with an amount is a row (nothing hidden); where the net result comes from, against `bkper group list` and `bkper account list` (the combining group, simple roots, or none, with `no_net_result`), and a calculated one as the CLI's Incoming roots minus its Outgoing roots, in total, before and every month, with no account under two roots. It also asks every root for each chart preference and checks the data of every chart that fits each report, the main one and every other view, against the CLI: each month of a chart by month, the parts of a breakdown chart (exactly the rows with an amount, positive in a donut, adding up to the root), each stacked part in every month (at most six) and their sum against the root, each compared row; that no bridge is drawn and one asked for is unfit as `no_bridge`; and that the main chart is one of the views, an unfit preference is not (a pie asked for is a donut), and no report offers more than six charts. Each line shows the preference, the main chart, the rule that chose it, the unfit preference's reason and the number of views. It also shows targets side by side (the activity or position roots, a root with a group or account under it, targets of different roots, a root with an account in no group; by month, a quarter, compared, a pie (a donut) and stacked asked for, today, the reverse order, a repeat, and with `--hashtag`), each checked against the CLI's query of that target alone as above, and that they read exactly the queries each reads alone, each once, in the order asked for, with no total, share or calculation, only charts that imply no whole, and that positions with activity are `mixed_targets`. It also reads each root's and the net result's default periods (this year or today, and the last 12 months by month) as a request that names none reads them (`readReport`), and checks that each reads the default period when it has movements and otherwise the last year with movements by the CLI's history, with exactly one more query, of the history, only then; those reports are checked like the others. The CLI shows raw balances negated for permanent accounts (Liability and Outgoing negative), so it flips a CLI amount when its row's `credit` equals its `permanent`. The app reads its own queries, with their variables; the CLI reads the same dates in ISO months (`on:` as `after:` and `before:`, as the CLI lists activity by month only for a query with `after:`), so the two forms must agree. Bkper resolves `$y`, `$m` and `$d` from its own today, so with `--today` every relative date, for the app's reads and the CLI's alike, is written in ISO as of that day, and `before:$d+1` reads through the end of its month.

`npx tsx scripts/verify-balance-line.ts [--root=<id or name>] [--month=YYYY-MM] <bookId>...` checks the line of a balance as of a day, read-only with your `bkper auth token`: for each position root (or `--root`), the reports of its balance now, at the end of last month and at the end of each `--month`, built from their own planned queries only (the balance's and its comparison's: no query for the line), show the 12 month-ends ending at their day; each of the 11 earlier points equals the CLI's balance of the root `before:` the next month, and the last the CLI's balance of the report's own dates (`before:$d+1` now), to the cent (flipped when `credit` equals `permanent`); the last point is the headline exactly; and the line is offered with those points whenever one has an amount, else not.

## Intent resolution

`resolveIntent(prompt, snapshot, { client, timing })` (`server/src/services/intent-resolver.ts`) turns a request in any language into a `ReportIntent` with ONE decision request to Jev, measured as `jev` in `Server-Timing`. It returns `{ recognized: true, intent, language?, trace }` or `{ recognized: false, language? }` (not a report). Jev makes judgments, code makes decisions.

- `intent-questions.ts` holds every question, criterion and threshold (`THRESHOLDS`) but the period's, which `period-questions.ts` holds (see Period questions); review and tune them there, together. Jev only chooses among options code offers, or answers yes or no: the root groups (by name, described by their nature and up to 60 subgroup and account names) plus `net-result` and `none`; the period's parts (see Period questions), whose options hold no date; five yes/no recognition questions (`over_time`: month by month; `composition`: broken down into parts; `versus_earlier`: compared with an earlier period it names; `year_earlier`: compared with the same period a year earlier; `bridge`: one amount leading to another, step by step); the chart word the request uses (`chart_named`, `CHART_NAMED_CRITERIA`: `pie` (a donut too; both are drawn as a donut), `bars`, `line`, `area`, `stacked`, `waterfall`, `table` for just the numbers, or `none`, with examples in several languages); the 133 Bkper languages (`report-shared/languages`). Each question stands alone: none refers to another or says when not to answer yes (a test checks the yes/no ones). State is only `{ request, today }`.
- Code applies the thresholds (`none` or an unsure root is not a report; an unsure or unspecified period reads the default period, marked `defaultPeriod` for the report (see Default period); an unsure chart word is `none`; the language is returned only when sure, ≥ 0.8), then the rule table `SHOW_RULES` decides how to show the report, the first rule that applies: `named` (the chart word: `pie` as `donut`; `line`, `area`, `stacked`, `waterfall` and `table` as themselves; `bars` by month over time, `compare` versus an earlier period, else `ranked-bar`); `bridge` → `waterfall`; `versus_earlier` → `compare`; `over_time_composition` → `stacked`; `over_time` → the `trend` view; `composition` → the `breakdown` view (a donut by the facts, else ranked bars); `auto` (the rules). `over_time` also sets `monthly`, and it, or a preferred chart by month (`bar`, `line`, `area`, `stacked`), makes the default period the trend one. The intent's period is the parts `readPeriod` reads (see Period questions), with its `compared` parts, or `compareWith: 'year_earlier'` when `year_earlier` is yes and no second period is named, whichever rule fired; a request that names no period reads the default period, compared a year earlier too when `year_earlier` is yes. A sure next year, month or quarter is `ReportError` `future_period`, before any balances query (after the root: a request of no root of the Book is still not a report). Which charts fit is decided afterwards by `buildReport`, from the facts.
- `trace` (`IntentTrace`) holds each judgment's answer and score (a choice's confidence, a yes/no's probability of yes, with `answer` after its threshold; each part of the period with the value read, `period` being its span), the rule that fired, `periodRules`, the rules of `readPeriod` that changed the parts, when any did, and `names`, the Book's names the request writes, when it writes any. Like the intent, it stays in the Worker: `createReport` returns both for tests and scripts, and no API response carries them.
- The hashtag comes from the request text (`extractHashtags`: the first one written; the others are left out), never from Jev, so a caller can start `hashtagQuery` in parallel with Jev.
- Names come from the request text too (`findPromptNames`, `prompt-names.ts`), never from Jev: whatever wrote the text (typing, autocomplete, a saved request, `q`, the Agent API), the exact names of the map's groups and accounts it writes are what the report is of, side by side when several (the first as `root`/`target`, the rest `alongside`, at most `MAX_NAMED`, 6), whatever Jev's root answer, `none` included. Jev is asked the same single decision request either way (byte for byte: no state or question is added), and its root is read only when the request writes no name, so a renamed group or account in a saved request falls back to the root Jev chooses, and the title shows it. The rules, in order, documented in the module, and shared with the web client's completion in `report-shared/names` (`matchNames`, `pickName`, the folding and the word boundaries), so both always agree: whole names ignoring case and accents (NFKD, lowercase, no marks, whitespace runs as one space), starting and ending at an `Intl.Segmenter` word boundary (so languages written without spaces work) or next to a character that is not a letter, mark or digit, and starting after a run of whitespace, not inside it (so a name after two spaces is still written exactly); never names of one character, nor names inside `#hashtags`; the longest match first, then the one that starts first, dropping any that overlaps one taken; colliding names (alike once folded): the one written exactly, then a group over an account, then Book order (each root with its subgroups, then its accounts, then accounts in no group); each once, in the order written. A group's root is its top-level group, an account in no group is its own root, and an account under several roots is named under a root another name can only be under, else the first root in Book order holding it; the report reads it from its smallest group either way (see Report balances). Code then decides from the names: their default period (by the first's nature: this year, today or the last 12 months; the report moves it, as any default, see Default period), and no composition side by side (they are no whole, so "Food and Rent by month" is a trend, not stacked parts); positions with activity stay `mixed_targets` when planned. Finding names indexes every name of the map on each request, with no cache: about 2 ms for 500 names and about 60 ms for 25,000 accented ones (measured locally).
- `decision-client.ts` is the TypeSafe SDK connector: the platform outbound placeholder key in the Worker, a short timeout and one retry for typing, and `BkperAiError` keeping the Bkper AI error `code` (such as `usage_limit_exceeded`) for routes to map.

`npx tsx scripts/eval-suggestions.ts <bookId>...` shows how real Jev ranks real Books' suggestions, read-only (maps with your `bkper auth token`; Jev with `BKPER_AI_TOKEN` or the same token, `bkper-ai-source: report-eval-suggestions`): every candidate with its probability, the three suggestions and the time and input tokens of the one request. Tune the question in `suggestion-questions.ts` against several Books at once, judging the order as the person opening the Book would, never by expecting a Book's answer. On 2026-11-10, nine Books (Bkper Finances, Bkper Finances 21 Final, Nimbus, Planejamento Financeiro Nimbus, Personal finances, 1.AAQ Services, DEMO Expense Reports, Aqua Tecnologia S/A, Rosália): the Book's profit and loss or net result first on five, its balance sheet or cash first on two (Bkper Finances and Nimbus, the profit and loss second or expenses next), expenses first on the two Books of expenses; 230–370 ms per ranking (866 ms once, cold), 450–3,350 input tokens. A tiny group whose name sounds central can still take the third place (Bkper Finances' `Summary`, two closing accounts): hiding it in the Book removes it. Asking what the Book's people would most want to see put net worth or cash first, and a 1-account group second; telling each group's share first and asking for the Book's main report fixed both.

`BKPER_AI_TOKEN=<token> npx tsx scripts/eval-intent.ts [--only=<n>,...]` asks real Jev ~105 multilingual requests on the two test Books (snapshots read-only with your `bkper auth token`; Jev with `BKPER_AI_TOKEN` or the same token), chart requests among them (short ones such as "despesas em pizza" or "費用 円グラフ" too) and requests that write the Books' group and account names (longest names, accents left out, several side by side, accounts in no group, in Japanese, Chinese, Arabic, Hindi and Korean among others), and reports accuracy of each part of the intent (root, targets, period, months, view, chart preference, what the period is compared with, a year's either way being the same) and the language, of the whole intent (chart included: a request that names no chart expects `auto`; one that writes no name of the Book expects no target; a request that names no period expects the period the Worker reads, after its default moves to the last year with movements, read-only, as in Default period), and p50/p95 latency. Each miss prints its trace: every judgment with its score and the rule that fired. The period is scored by meaning: the expected period id and `compareWith` (`periodRequestOf`) and the intent's period are built and resolved at the Book's today and must read the same months, of the period and of its comparison (a request that names no period may also read the months of the default the Worker reads, such as a balance now); what the period is compared with is scored the same way. Bkper AI caches identical requests for 15 minutes, so only a run after a change measures real latency. Tune the questions, never the expected answers. It, `eval-periods` (below), `eval-suggestions` and `eval-round-trip` (see Request text) are the only development scripts that call Bkper AI (`ai.bkper.app`) by default, because Jev exists only there and the deployed app uses it; translating strings and reviewing the docs agents read need no Bkper AI, and call it only with `--ai` (see Strings and Docs for people and agents).

`npx tsx scripts/eval-periods/run.ts [--mode=atomic] [--only=<n>,...] [--category=<c>,...] [--language=<code>,...] [--concurrency=4] [--out=<file>]` evaluates how requests' periods are read, on real Jev (snapshots read-only with your `bkper auth token`; Jev with `BKPER_AI_TOKEN` or the same token; 4 requests at a time, transient Bkper AI errors retried). `scripts/eval-periods/cases.ts` holds 561 requests in 14 languages (Arabic-Indic, full-width and Devanagari digits, abbreviations such as Q3, YTD, LTM, MoM and YoY, typos), each with the today it is asked on (2026-01-15, 2026-03-31, 2026-11-09, 2026-12-31, 2028-02-29), a category, a paraphrase group, and the period a person means, written as the parts of `period-query.ts` (equally right readings both accepted; a request that names none expects none). A mode (`modes.ts`) is one function from a request, the snapshot and the today to the parts of a period, with the model's judgments, latency and tokens; the one mode, `atomic`, asks the app's request (`buildIntentRequest`, its `today` replaced) and reads the parts with `readPeriod` (a next year, month or quarter as `future_period`), and another way of reading periods can be measured against it as another mode. Scoring (`score.ts`) builds the queries of the expected and of the read parts at the case's today, resolves them with `resolveQueryDates`, and compares the months of the period and its comparison, or the reasons (`future_period`, `comparison_not_earlier`, …): accuracy per part (span, year, month, quarter, comparison), per whole request, per category and per language, consistency (paraphrase groups whose members all read the same months), p50/p95 latency and input tokens; it prints every miss with its judgments and writes the run to `/tmp/report-eval-periods-<mode>-<time>.json`. `--compare=<a.json>,<b.json>` shows two runs side by side per part, category and language, with consistency, latency, input tokens and request characters, and lists the requests that got better or worse. `test/eval-periods.test.ts` checks the scoring, and that every case's expected parts build a query (or the reason of its category) and the categories, todays and languages keep their minimum counts. Tune the questions, never the expected answers.

`npx tsx scripts/eval-periods/e2e.ts [--all] [--only=<n>,...]` sends requests of the period evaluation through the app's report pipeline end to end: `createReport` with a prompt, real Jev, and the app's balances loader reading the live Book, read-only, texts in English. ## Query reports

`server/src/services/query-report.ts` (`planQueryReport`) and `buildQueryReport` (`report.ts`) report a Bkper query, such as the one a Book shows its transactions with, read exactly as sent, with no Jev: the query is the report's balances query, so every amount it shows is the one Bkper's own sidebar shows for that query, future-dated transactions included. Nothing in it is rewritten, cut off at this month or moved to a whole period, and no period is `future_period`. A prompt that is a Bkper query (`isBkperQuery`: a `group:`, `account:` or `acc:` term with a value) is read the same way, so a query report's `text`, the query itself, reopens it from a state, `q`, the shelf or the input.

- Terms (`parseQuery`): `group:` and `account:` (`acc:`) names, quoted with either quote or bare, the `after:`, `before:` and `on:` terms and where each is written, and whether it asks `by:m`. Everything else (hashtags, amounts, text, `is:`, `AND`, `OR`, `NOT`, `-`, parentheses) is Bkper's to read: one hashtag filters as Bkper's balances do.
- Names are found as Bkper finds them (`bkperName`, after `StringUtil.normalize`): without `?%*+@#!~\`'":;=\|$^`, runs of whitespace, `-` and `_` as one `_`, lowercase, without accents; a `group:` among the map's groups at any depth, an `account:` among its accounts (in no group too). Several are side by side in the order written, each once, at most `MAX_NAMED` (6), the first found; names the Book does not have are left out, and they are checked as an intent's subjects (`subjectNodes`: `mixed_targets`, `mixed_group`). None found: `QueryNotAReportError`, API 422 `query_not_a_report`, before any balances query. Names Bkper's answer leaves out (an account it does not find by its name, an archived one at zero) are left out of the report; none left is `query_not_a_report` too.
- Amounts: each group's and account's balance in the answer to the query itself, its period balance for activity and its cumulative balance for a position (the nature of the first name), its rows the groups and accounts Bkper lists under it. Two more queries, read in parallel, never change them (`queryReportQueries`):
  - months, for charts by month and the table's trend: the query with ` by:m` (the query itself when it asks `by:m`), shown only when Bkper answers it with the same groups and accounts at the same totals (`sameTotals`; without `by:m` Bkper may answer a year written as `on:2026` in one bucket). The months shown are those of the days read (`queryMonths`): from the month of `after` (else the first with a bucket) to that of the last day read (else the last with a bucket, as far as future-dated transactions go); a position with no `after`, the 12 month-ends ending at its last day (`BALANCE_LINE_MONTHS`), its last point the headline. With none, no chart by month.
  - the comparison (`previousDays`, `comparisonOf`): the query with the period before written in place of its own date terms, in the Book's date format, everything else as sent: as many whole months before when both ends are first days of a month, else as many days; up to a day from the start of the Book, up to the end of the month before. None with no end (`after:` alone, no dates), a date it cannot read, a date field written twice, or `on:` with `after:` or `before:`. It is shown only when Bkper's labels say it read exactly the days meant, for the query and for the comparison.
- Dates are read here only to write the comparison (`queryDays`): in the Book's date format (`d/M/yyyy`, `M/yyyy`, `yyyy`, and `d/M` of this year, as the format orders them), ISO (`yyyy-mm-dd`, `yyyy-mm`) or bare variables (`$d`, `$m`, `$y`, `±n`); `after:` from its first day, `before:` up to its first day, `on:` its whole day, month or year (`after:` and `before:` over `on:`, as `QueryRange.getFuzzyRange`).
- The period (`QueryRead`, `kind: 'query'`) is the days Bkper says it read (`readQueryDays`, its labels in the Book's date format, either end open; else the days read here), written as days (`Labels`): a range of days (`Jan 1 – Dec 31, 2026`), a position or a range from the start of the Book as of its last day (`As of Dec 31, 2026`), `after:` alone through the last month shown, no dates all time; labels it cannot read show Bkper's range as written. The comparison is named the same way.
- The report has no intent: its spec's `request`, and so the response's `text`, is the query; its `query` and Source are the query as sent, and Open in Bkper opens it. It names no view; the request's `chart` applies as for a prompt.

`npx tsx scripts/verify-query.ts [--api=http://localhost:8809] <bookId>...` checks reports of queries end to end against the bkper CLI, read-only, with your `bkper auth token` and the local Worker (`npm run dev:server`): for each Book it picks from the map an activity root and a position root, mixing nothing, two accounts and a subgroup under the activity root, and the last year before this one the activity root moved in and its last month with movements (from the CLI), and writes queries as a Book does, in its date format: that year, month and quarter; days of that month, as written; the accounts and the subgroup side by side; terms Bkper's balances ignore (amounts, `is:`, two hashtags, text); the year with `on:` in ISO; this whole year, through its last day; a balance at the end of that year and of this one; and a balance with no dates; and a Book's known references (`REFERENCES`: on Bkper Finances, `group:'Net Income' after:01/2026 before:01/2027` is -3,584.16, future-dated amortization included, and `group:'Bkper Balance Sheet' before:01/2027` -17,669.04), whose headline must be exactly that. Each report must answer with the query sent as its `query` and `text`, and every amount it shows (each Answer and every breakdown row at any depth) must equal the CLI's balance of its group or account for the same query, sent as is, to the cent (flipped when `credit` equals `permanent`; a query with `after:` or `on:` summed over the CLI's columns, any other its last), every row the CLI lists with an amount must be shown, and a query of no group or account must answer `query_not_a_report`. An account the CLI does not find by name is skipped and said.

## Report spec and catalog

`buildReportSpec(report, lang)` (`server/src/services/report-spec.ts`) turns report data into a json-render spec of the report catalog (`report-shared/catalog`), and validates it before returning it.

- The spec is the standard flat json-render spec (`root` plus an `elements` map of `{ type, props, children?, on? }`), built with `defineSchema`/`defineCatalog` from `@json-render/core`, pinned exactly, without React. Components: `Report` (the root, the only one with children; with the `request` the report answers, see Request text, and a `notice` when it could not compare, or draw the chart asked for, as asked), `Answer`, `Chart` (the main chart; left out when it is the table), `Visualizations`, `BreakdownTable`, `Source`.
- Targets side by side have an `Answer` each (`answer-1`, `answer-2`, …, in order, each labelled with its name), and none for them together; the title is their names as a list in the language (`Intl.ListFormat`, each isolated); the BreakdownTable (labelled `chart_side_by_side`) holds the targets with no `total`; ranked bars and compared are labelled `chart_side_by_side` rather than `chart_breakdown`, so nothing reads as parts of one whole. The catalog is unchanged: several Answers were always valid.
- `Visualizations` (after the Chart in the spec for compatibility; the renderer places previews beside the title, above the chart; left out when only the main view fits) holds `main` (a `VIEW_KINDS` kind) and `views`: every chart that fits, at most six and the table, each with its `kind`, a short localized `name` (`chart_name_*`) and, but for the main one (its data is the Chart's) and `table`, its full `Chart` props, the same a preference for it would draw. It binds `selectChart` (local, the renderer passes the kind). Its `unfit` stays in the v1 catalog but is no longer given: a preference that does not fit is said in the Report's `notice`, one line, `notice_chart_unfit` (`Can’t show {chart}: {reason}.`) with the chart's name and a localized reason (`chart_unfit_*`) naming, for a negative part, the row and its amount (formatted exactly with `Intl` and the Book's decimal places), each isolated; after the comparison's notice when both apply.
- `Chart` kinds, each with strict props: `bar`, `line` and `area` (months and series), `stacked` (months and 2+ series without `line`), `ranked-bar` and `donut` (items of breakdown rows; no `pie`, which reports draw as a donut), `compare` (items with `value` and `previous`, and `periods`: the names of the period and the previous one, for a legend, in the form of the subtitle and the comparison (see Period labels)) and `waterfall` (`start`, floating `steps`, each with the `rowId` of its row unless it is the rest, and `end`), which the v1 catalog keeps and renderers still draw, though reports no longer give one. Breakdown row kinds `other`, `incoming` and `outgoing` and the Answer's `parts` stay in the catalog likewise, unused. `Source` has `calculated` (`{ label, note }`) for a net result Report calculates, and the optional label `details` (`source_details`) of its disclosure; renderers name it by `source` in specs written before. Actions: `expandRow` (local, the renderer passes the row), `selectChart` (local, the renderer passes the kind) and `openInBkper` (only where the renderer can navigate).
- `validateReportSpec` checks the catalog (components, actions, strict props of each element), json-render's `validateSpec` (including unreachable elements), that the root is a `Report`, and that a spec has at most one Chart and one Visualizations, whose `main` is the Chart's kind (`table` without a Chart), each other view carries the data of its kind, kinds appear once, and the unfit kind is not among them. Renderers may call it on specs they receive.
- Every text is resolved in the spec, in the report's language: titles, period labels (see Period labels), comparisons, the note on a net result Report calculates, and every label a renderer shows. Group and account names stay verbatim, also as row labels.
- Values written into a text (a period, a date, a name) are isolated with `isolate` (`report-shared/bidi`, FIRST STRONG ISOLATE … POP DIRECTIONAL ISOLATE), so dates and Latin names read in order in Arabic or Hebrew, and Arabic names in English. Where a text is read as words rather than shown, such as the request in `url`, `withoutIsolates` takes them out. Numbers in texts, like a quarter's, use the language's digits.
- A net result Report calculates has a BreakdownTable `total` row (the net result) under its roots, a chart by month with a series with `line: true` (the net result) over their bars, and the Source's `calculated` label and note. A net result of a combining group is that group's report, titled by its name, with nothing calculated.
- Amounts and ratios stay the report's decimal strings, and months and instants stay ISO; renderers format them with `Intl` in the Report's `locale`, with its `fractionDigits`, in its `dir`.

## API

`server/src/api/routes.ts` adapts HTTP; `server/src/services/report-service.ts` (`createReport`) and `suggestions.ts` (`readSuggestions`) hold the behavior.

- `GET /api/v1/books/{bookId}/names` — `{ names: [{ id, name, kind, root }] }`: every group and account of the map, each once, in Book order (as `findPromptNames` orders them, `bookNames`), `kind` `group` or `account`, and `root` the root group holding it (itself for a root or an account in no group; the first in Book order for an account under several). Served from the KV snapshot, so up to 60 s old, with the same permission as the suggestions; for completing requests as they are typed.
- `GET /api/v1/books/{bookId}/suggestions?language=` — `{ suggestions: string[], problem? }`: up to 3 example requests (`SUGGESTION_COUNT`) in the language, the main one first; their intents stay in the Worker. Code offers the candidates from the snapshot (`suggestionCandidates`, `suggestions.ts`): each root group and each group directly under it, as the person sees them in the Book (none the Book hides, `hidden`, nor under one), with accounts with transactions posted and not archived under them, and no group `mixedGroupProblem` would refuse; each as its natural report: a position today, Incoming and Outgoing together (the Book's own profit and loss, which stands for the net result) in total this year, Incoming or Outgoing alone by month this year; and the net result only when Report calculates it (`netResultOf` `calculated`). At most `MAX_CANDIDATES` (20), the largest by those accounts, ties in Book order. Jev ranks them with ONE choice (`suggestion-questions.ts`, which holds the question): the main report of the Book, the one its people check first to see how they are doing. Each option tells first its share of the Book's accounts with transactions posted (so a small group reads as small whatever its name), then its nature, its parent and how it is shown, and up to 8 names it contains; never an amount. Its probabilities order every candidate; code takes the first three, skipping one that would show the same as one already taken (`alike`: a group directly under or over it, or of the same nature sharing accounts; income and expenses together and their expenses are different reports). The order is remembered in KV for 30 days by a hash of exactly what Jev is asked (`suggestion-order:v1:<sha256>`), so a map is ranked once, and a changed map (a group renamed, moved, hidden, an account posted to) is ranked again at once; the language and today are not part of it. When Jev fails (or the Bkper AI allowance is out), the candidates follow Book order and nothing is remembered. `jev` in `Server-Timing` marks a ranking. Periods follow the rule of a request that names none (`readSuggestions`, through `readReport`, see Default period): activity this year, else, when this year has no movements, the last year with them, after at most one history query per suggested report (never one per group), and the text names that year (`suggestion_*_year`: "Expenses by month in 2018"); positions today, with no query. Their intents hold the period as parts: this year `{ span: 'year', year: 'current' }`, the year moved to as written, today `{ span: 'now' }`. So `/suggestions` waits for the suggested activity reports' own queries (in parallel), which the prefetches then read from the balances cache; a suggestion whose balances cannot be read keeps this year. The suggestions of `not_a_report` are read the same way, and are texts too.
- A `/report` prompt that is exactly one of the Book's current suggestions (`findSuggestion`: whitespace runs as one space and trimmed, case kept, as the client's request keys) in the requested language, else `Accept-Language`'s, else English, is that suggestion's intent, with no Jev decision, and its report is in that language; any other prompt is read by Jev. Only a prompt some candidate could be written as (its default period, or a year the prompt writes) ranks and reads the suggestions (the ranking and balances caches above), so other prompts cost nothing more; a request reads each balances query once (`readOnce`), so the suggestion's report reuses what its suggestion read. When the Book has `empty_book` or `nothing_to_report` (see Book problems), it returns `{ suggestions: [], problem }` instead, reading no balances. It also warms the snapshot.
- `POST /api/v1/books/{bookId}/report` — body `{ prompt | query, chart?, language?, format? }`, exactly one of `prompt` or `query` (else 400 naming `prompt`): `prompt` is read by one Jev decision (none for a suggestion's text, see above); `query`, a Bkper query of at most 2,000 characters, read exactly as sent with no Jev (see Query reports; so is a `prompt` that is a Bkper query), its report in the requested language, else `Accept-Language`'s, else English; an intent is never accepted (strict body: an unknown field is 400), nor answered. `chart` (`REPORT_CHARTS`) is how to show the report, not what it is: it replaces the chart the prompt names, with the same rules as an intent's preference, and the report's `text` never names it. `spec` (the default) returns `{ spec, text, language, query, dataAt, chart, url }`, where `text` is the report's own text (see Request text), and `chart` is `{ kind, fallback, asked? }`: the main chart (`none` for none), whether the chart asked for did not fit, and that chart (the request's `chart`, else the one the prompt names, a pie as `donut`; left out for none or `auto`), which a client sends back as `chart` with the text to reopen the report as it was asked for (see Report state); the charts that fit are the spec's `Visualizations`. The intent and the trace stay in the Worker (see Intent resolution). `html` returns the report file (`text/html`, see Report file). Errors stay JSON.
- Order of work: `getUser`, then the KV snapshot (its key needs the user, and Dispatch passes no identity), then Jev, whose options come from the snapshot, then the report's balances queries, in parallel, which need the intent's subject and period; for a default period without movements, then its history query and the queries of the last year with movements (see Default period). Jev answers in ~0.3 s when called often but ~1 s after some idle seconds; that, not the app, is most of the prompt path's p95.
- Language: the `language` field (any BCP 47 tag of a Bkper language, `supportedLanguage`), else the one Jev is sure of, else `Accept-Language`, else `en`.
- `url` opens the request in the Report app (`?book=&q=`), on the preview host when the API was called there, else production. `q` is the prompt.
- Errors use one envelope, `{ success: false, error: { code, message } }`, with the app's own messages, never the prompt or upstream details (`api/errors.ts`): 400 `invalid_request` (naming the field), 401 `unauthorized`, 403 `forbidden` (also for a Bkper 401, its answer to a user who is not a collaborator: the platform has already authenticated the caller), 404 `book_not_found`, 422 `not_a_report` (with `suggestions`, texts), `query_not_a_report` (a `query` that names no group or account of the Book; the web client, which sends one only to follow the Book, then leaves its report as it is), `future_period`, `unknown_root`, `unknown_target` (the client's `error_unknown_target`: a saved or shared target deleted or moved), `mixed_targets` (`error_mixed_targets`: positions and activity side by side), `no_net_result`, `empty_book`, `nothing_to_report` and `mixed_group` (the last four with `problem`, see Book problems; their messages tell an agent to offer organizing the Book's groups, groups only, to an OWNER or EDITOR), 429 `ai_allowance_exhausted` (Bkper AI `usage_limit_exceeded`), 502 `upstream_error` (Bkper or Bkper AI), 500 `internal_error`.
- `Server-Timing` on every API response: `user`, `kv`, `book` (loading the map from Bkper), `balances`, `jev`, `compute`, `render` and `total`.

`npx tsx scripts/measure-api.ts [--base=<url>] [--runs=<n>] [--cold=<n>] [--hashtag=<tag>] <bookId>...` times the suggestion (each by its text, no AI), prompt and hashtag paths of a running app (default the local Worker) from `Server-Timing`, read-only, with your `bkper auth token`: `warm` with the snapshot cached and the report's balances read from Bkper (`balances`), `cached` with both cached, and, with `--cold`, `cold` after the caches expire (the map loaded, `book`). Prompts name a root and a period, so runs read other balances (a suggestion asked again within a minute reads none); prompts vary so Bkper AI's 15-minute cache of identical requests is not measured, but a rerun within 15 minutes repeats them.

`npx tsx scripts/measure-api.ts --flow [--base=<url>] [--cold=<n>] [--runs=<n>] [--offset=<n>] <bookId>...` measures instead what a person experiences (`scripts/measure-api/flow.ts`), read-only: opening each Book as the web client does (`AppState`: `GET /prompts`, `/names` and `/suggestions` at once, in parallel, then each suggestion's report by its text in the suggestions' language, in parallel, once the suggestions arrive; the Book's name comes from Bkper directly, not through the app, so it is not measured), `--cold` times (default 2) after waiting until its caches expired (65 s since the script last touched it), each followed by `--runs` warm opens (default 2), and after each open two typed prompts, sent as the client sends them (`{ prompt }` only; the 250 ms debounce is not included), in alternating order: one writing exactly one of the Book's names (from `/names`, checked with `report-shared/names`), and one writing none, so Jev chooses the root. Prompts are chosen deterministically per open (`choosePrompts`), never a suggestion's text (the client shows those from memory), each open with another period, so Bkper AI's 15-minute cache is not measured; `--offset` shifts them for a rerun within 15 minutes. Per Book it prints, cold and warm, p50/p95 of each step's time since the open began and of its own request, wall clock as the client sees it, with its `Server-Timing`: the shelf, the names, the suggestions, each prefetch, the open ready (all of them), and each prompt. Failed requests (such as a `not_a_report` the plain prompt can get) count in the percentiles and are marked. It never saves to the shelf.

## Saved prompts

`/api/v1/books/{bookId}/prompts` is the Book-shared shelf of original prompts, not computed reports. `/report` remains read-only. The client shelf sits just above the fixed bottom input (`components/report-shelf.ts`), remains visible through reports, typing and pending/error states, and replaces the initial suggestions once saved prompts exist. Its single row scrolls sideways instead of growing the footer. Each prompt is its own label (visually truncated, full text accessible), opens through `AppState.openSavedPrompt` (from memory within a minute, else resolved again; the first opens by itself when the Book opens with nothing asked, see Web client), and ends in a small menu (see below). Save needs one click and uses only the successfully shown report's original prompt; it is disabled while pending, already saved, or transitioning to the next report, and absent without a real source or server save capability. Mutation/list failures stay local to the shelf, with safe retries and an explicit reload for current access; reports and input remain usable.

- The chip menu is a `wa-dropdown` whose trigger is the chip's own last `wa-button` segment (a `⋯` drawn in inline SVG, as `wa-icon` would fetch and a strict content security policy blocks it): Move first, Move left, Move right, a divider, then Remove. Left and right are what the person sees, so in right-to-left languages Move left moves the prompt later in the row (`moves`, from the interface language's direction). A move that cannot happen is disabled, and so is every item while another mutation is pending (`canMove`, `canRemove`). The moves show only with `capabilities.move`, Remove only with `capabilities.remove`, and there is no menu without either.
- A move is applied once its menu has closed (`wa-after-hide`), so the menu fades where it opened rather than following its chip. The chip then scrolls into the row's view and keeps the focus on its menu button, and once the server confirms the order, the shelf's status region announces `shelf_moved` (its place and the count, until the shelf changes again). Moving or removing a chip in the DOM drops the focus it held, so a render that does so gives the focus back to the same control of that chip, or of the chip now in its place after a removal. Move errors show with the other shelf errors (`shelf_move_error`), with the same reload.
- Chips also reorder by dragging (`components/shelf-drag.ts`, `ShelfDrag`, a Lit reactive controller on pointer events, no library), only while `canMove` and with two chips or more; the menu's button never drags. A mouse or pen drags from the prompt segment after `START_DISTANCE` (4 px), so a plain click, even one that wobbles less, still opens the report; a finger after a long press (`LONG_PRESS_MS`, 350 ms, moving less than `TOUCH_SLOP`, 8 px), so a swipe still scrolls the row. The click that ends a drag, or the release after a cancel, is swallowed; a long press shows no browser menu, and a non-passive `touchmove` listener keeps a lifted chip's finger from scrolling the row or page.
  - The person always sees where the chip lands: lifted (the quiet brand fill and loud brand border, a small shadow), it follows the pointer along the row, drawn whole inside it (`inside`), while the chips between its place and where it lands slide aside by its width and one gap (`slideOffsets`), opening a gap exactly its width there. Where it lands is where its center has passed the others' centers in the row's reading direction (`dropIndex`), so right-to-left rows read from the right; past an end, it lands first or last. Near an end it was moved toward, the row scrolls, faster closer to it (`edgeScroll`).
  - Escape, a lost pointer or window focus, or the shelf changing under it put it back. Leaving the row above or below by more than its height (`leftRow`) closes the gap where it was and shows the chip back in its place; releasing there puts it back, and coming back into the row picks up the drag again. Dropping it elsewhere moves it with `SavedPrompts.move` (`beforeOf` gives `before`), announced as the menu's moves are; a failed move restores the order.
  - Smoothness: everything a frame needs is measured once at pickup; pointer moves are coalesced to one `requestAnimationFrame`, which writes only transforms, and the shelf does not render while dragging. The drop renders once, and the chips slide from where they were shown to their places (FLIP, Web Animations), the dropped one in `--wa-transition-fast` as it is already beside its gap, others in `--wa-transition-normal`, also when a failed move restores the order; a chip still in its layout place keeps the slide it has. A dropped chip lands without waiting for the server's answer, and the row is not scrolled to a focused chip while a drop settles. With `prefers-reduced-motion`, nothing slides: the others jump aside and the drop and rollback are instant.

- `SavedPrompts` (`client/src/state/saved-prompts.ts`) holds the active Book's `items` in the server's order (each id once), server `capabilities`, `loading`, pending `saving` prompt / `removing` id / `moving` id, and separate typed `loadError`, `saveError`, `removeError`, `moveError` reasons (localized by the shelf UI). `canList`, `canSave`, `canRemove`, `canMove` are UI hints, never authorization. `open` resets and reloads on Book changes; `load` retries/coalesces loads. `save()` saves only the shown report's source supplied by AppState, skips already saved prompts and coalesces repeated clicks; `remove(id)` is idempotent. `move(id, before)` (`null`: the end) is the one optimistic mutation, so a reorder shows at once: the items reorder before the request, the server's answer replaces them (its order wins), and a failure restores the order they had; `shelf_changed` or `prompt_not_found` (the shelf on screen is stale) also lists the shelf again. A move that changes nothing asks nothing. `beforeFor(id, 'first' | 'earlier' | 'later')` gives the `before` of each one-step move, or `undefined` when it cannot. One mutation at a time; a confirmed save goes last (one saved again keeps its place), a confirmed removal leaves, and other failures leave items intact unless Book access is denied; a forbidden save, removal or move turns all three capabilities off. Mutations invalidate older lists; session guards and abort signals drop late successes/errors even across A → B → A. Later explicit reloads follow KV's eventually consistent view.
- `Reports.originalPrompt` belongs to the successfully shown output, survives chart choices and later typing, and is the request's text, as asked. A suggestion is a prompt like any other: chosen, it is the source and can be saved; so is the text of a report opened by its state. Prompt-generated cache entries retain their actual original request, not later casing/spacing. `AppState` supplies this source to `savedPrompts`; never pass the input or a generated title to Save. With no source, Save is unavailable.
- `AppState.openSavedPrompt(id)` reads the active shelf item and calls `Reports.runSaved(prompt)`: the client's report of exactly that text from the last `CACHE_MS` (60 s), else a prompt-only singular `/report` request, so after a minute relative periods resolve again. Never the report of another spacing or casing, or one asked for with a chart; a saved text equal to a suggestion's shows the suggestion's report from memory, which the Worker would also build for it. A repeated click while it is on its way asks once. Saved executions populate the client caches like typing. AppState starts shelf loads after auth alongside reports and Book details, wires Book navigation and source changes, and leaves first rendering unblocked.

- `GET /prompts` returns `{ prompts: [{ id, prompt }], capabilities: { list, save, remove, move } }`, the prompts in the shelf's order (see the storage rules below). Every known non-`NONE` Book role may list: `OWNER`, `EDITOR`, `POSTER`, `RECORDER`, `VIEWER`. Unknown, missing and `NONE` roles are denied. Listing the shelf grants no balance access: the singular `/report` and `/suggestions` retain their separate VIEWER/POSTER/EDITOR/OWNER allowlist, so RECORDER can list prompts but not compute reports.
- `POST /prompts` accepts exactly `{ prompt }` and returns the saved `{ id, prompt }` (200, also on an identical retry). `DELETE /prompts/{promptId}` returns 204 even when absent. `PUT /prompts/{promptId}/position` accepts exactly `{ before: <id> | null }` (`null`: the end) and returns the whole shelf in its new order, the shape of `GET /prompts`; a `promptId` not on the shelf is 404 `prompt_not_found`, a `before` not on it 409 `shelf_changed` (the caller lists again). Only `OWNER` and `EDITOR` may save/remove/move, and either may remove or move any shelf item.
- `services/saved-prompts.ts` performs one fresh, thin `bkper.getBook(bookId)` on **every** read/write before accessing storage. It never authorizes through a cached balances snapshot, the current caller’s billing plan, or client-supplied capabilities. A list’s capabilities describe that request, not future authorization. Shelf responses use `Cache-Control: no-store`.
- Prompts follow the current report-request rules (`services/report-prompt.ts`): trim the edges, 1–1000 UTF-16 code units; preserve internal whitespace, case and language. Nothing is resolved or computed when saving. No HTML, intent, resolved dates, amounts, inferred language or separately selected chart is stored. To reopen, send the saved text as `prompt` to the existing singular `/report`, so relative periods resolve again.
- Storage is the existing app KV binding, one durable key per item: `saved-prompts:v1:<encodeURIComponent(bookId)>:<id>`. `id` is lowercase SHA-256 of the JSON-encoded prompt; the value is only that JSON string (encoding preserves all UTF-16 text). There is no TTL, user partition or whole-list read/modify/write. Identical saves address the same item; independent saves/removals cannot overwrite one another. Listing follows every KV page, checks stored data, tolerates an item removed before reading, and returns the shelf's order.
- Order is the KV key's metadata, `{ position }`, a fractional index from `fractional-indexing` (only the server computes it, and never exposes it): the leftmost prompt is first. Prompts without one were saved before the shelf had an order and sort first, by id; then by position, compared by code unit; equal positions (concurrent saves or moves) by id. Metadata is either absent or exactly a valid `{ position }`; anything else is `storage_error`, like a corrupt value. A save lists the keys (not the prompts): a new prompt goes after the last position, and a prompt saved again is rewritten with its own metadata (none when it had none), so it keeps its place. A move reads the shelf, writes nothing when the prompt is already in place, gives the other unpositioned prompts positions once, in their order, before the first positioned one, then writes the moved prompt between its new neighbours (when its two neighbours share a position, it goes just after that position, and `before` and the prompts after it that share the position are rewritten after it). Each write rewrites one item's own value with new metadata, and only items this request read, so a prompt removed before is not saved again. The response is computed from this request's reads and writes, never by listing again, as KV may not show them yet. KV visibility is eventually consistent: a successful write need not appear immediately on another replica; same-item save/remove races follow KV ordering, and a later save can restore a removed item. This is not a linearizable shelf. KV failures return 502 `storage_error`, without prompt/key/upstream details; a failed write may have reached storage, so identical retries are safe.
- Native evidence (paths from `/workspace`): `bkper-core/api/src/main/java/com/bkper/books/savedquery/SavedQueryController.java` lists via `Authorizer.assertCollaboratorOn` and saves/deletes via explicit `OWNER`/`EDITOR` checks; `books/collaborator/Authorizer.java` denies only `NONE` for listing. Native saves additionally check the **owner’s** free plan (`users/user/BkperUser.java:isToBlockSaveQueries`), unlike deletion. That billing restriction is deliberately **not inherited** by app metadata; only the verified Book role model applies.
- Native saved queries are executable (`bkper-clients/packages/pwa/client/src/book/services/query-service.ts`, SDK `Query.getQuery`, canonical `bkper.Query.query`). They have no metadata discriminator and must never carry natural-language prompts. Their native repository uses per-entity transactions (`books/savedquery/SavedQueryRepository.java`), but is not a suitable shelf. Book properties also are unsuitable: `books/book/BookService.java` and `BookEntity.setProperties` replace the entire map, risking lost concurrent changes. The installed SDK types (`node_modules/bkper-js/lib/index.d.ts`, `node_modules/@bkper/bkper-api-types/index.d.ts`) expose `Book.permission`, properties and executable queries, but no owner-plan capability or per-property atomic mutation.
- All mutation tests inject clients and isolated storage and prohibit network access. Never test writes against real Books. No app installation or installation requirement is added.

## Report state

`report-shared/url-state` writes a report as the opaque app state Bkper keeps in a Book's URL (`appState`, at most 1,024 of `A–Z a–z 0–9 _ -`), so a link, Back or a reload opens it again by asking for it: `encodeUrlState({ text, language, chart? })` and `decodeUrlState(state)`.

- What a person would send to ask for the report again: its own `text` (the response's, which sent back as a prompt asks for the same report, see Request text), its `language` (Jev often reads a short text's language wrong, so it goes with it) and the `chart` to show (`REPORT_CHARTS` but `auto`): the one chosen from the previews, else the one the report was asked for (the response's `chart.asked`), as its text never names a chart (`Reports.reopen`). Reopened, it is `POST /report { prompt: text, language, chart? }`: read by Jev, or with no AI when the text is a current suggestion's or a Bkper query (a query report's text is its query, see Query reports).
- A version, `5`, then the base64url of the UTF-8 of `<language>.<chart>.<text>`: the chart empty for none, the text last, so it may hold anything. The text is a request the API accepts (trimmed, 1 to 1,000 characters); a state longer than 1,024 is no state, so a very long text, or one in a script of three UTF-8 bytes a character over about 250, keeps none and the report is not kept in the Book's URL.
- Decoding accepts only a state it writes itself (it encodes the result again and compares): any other value, such as the compact intents of versions `1` to `4` written before, is no state, and the request in `q`, if any, runs instead.
- The report file carries the state of its report (`open`), and of the same report as each other chart that fits (`open.charts`, with that `chart`), and the web client sends and reads it in a Book and keeps it in its own URL (see Web client). A chart chosen from the previews is the report's state with that chart, so reopening shows it.

`npx tsx scripts/verify-open-in-report.ts [--app=<url>] [--api=<url>] [--prompt=<text>] <bookId>` checks opening a report from the Agent end to end (the Book's first suggestion, by its text, or `--prompt`, such as one naming an Account), read-only, with your `bkper auth token` and the app running locally (`npm run dev`): headless Chromium plays the Book and the Agent at their origins, as bkper-clients implements them, with the real report file from the local API and the real app in the Book's panel. It chooses a chart from the file's previews, then checks that the chart shows in the file with nothing sent or loaded, that a click on the file's link opens the Report app in place of the Agent with the state of the report as that chart, that the app asks for that report by the state's text, in its language, as that chart (every report asked by a text in its language: a state's or a suggestion's), with that text in the input, that choosing another chart in the app sends its state to the Book once and asks for no report, that choosing another report sends its state to the Book once, that a state the Book goes back to shows its report again without being sent back, and that the file reaches no network and nothing logs an error.

## Docs for people and agents

`README.md` is the listing page people read (`bkper app get report` shows it too), short and in the format of the other apps' listings: an opening that says what a report shows and that it is read-only with every number from Bkper (an agent loads the README twice, as Markdown and HTML, so every line costs it), how to open it, examples in several languages, the charts one can ask for and why one is not drawn, saving requests, its limits, opening a report from the Agent, and a collapsed API section (`<details data-toc>`) with every route and the report call. Detailed rules belong in the OpenAPI texts, where agents read them; keep development notes here, not there.

Agents decide from `bkper app list -b`, `bkper app get report` and `bkper app api spec report`, so the OpenAPI texts are written for them: the document's `info.description` (`server/src/api/openapi.ts`) is the guide, and each route, field and error repeats what an agent needs where it reads it (`routes.ts`, `schemas.ts`). The call they lead to: `POST /api/v1/books/{bookId}/report` with `{ "prompt": <the person's words, in their language>, "format": "html" }`, its output saved to an `.html` file the agent publishes, as its one call: the README (which `bkper app get report` shows, so an agent needs nothing more) and the OpenAPI texts say not to ask for `spec` first, query the balances or re-check the amounts, as agents did otherwise, taking twice as long. `spec` is what the web client renders. `bkper app api request` prints only an error's `message`, so messages say what to do next (`api/errors.ts`), never the request.

After changing the README, the listing's `description` or the OpenAPI texts, review them yourself as that fresh agent would read them, with no Bkper AI: from `README.md`, `bkper.yaml` and the OpenAPI document alone (`npm run api` regenerates it), would it run the report call above on the Book, with the request in its own words and `format: html`, save the output and publish it, and change nothing in the Book? `scripts/agent-docs/plan.ts` lists exactly what a plan must do. `npx tsx scripts/check-agent-docs.ts --ai [--spec-url=<url>/openapi.json] [--model=<id>]` asks a Bkper AI language model instead, only when the person asks for it: it gives only the README, the listing and the OpenAPI document (this folder's, or a running app's) to the model playing a fresh agent, asks it for the commands it would run for report requests in four languages, and checks them with `judgePlan`. Nothing runs and no Book is read. Without `--ai` it calls nothing and exits.

## Report renderer

`<report-view>` (`client/src/report/`, entry `index.ts`) renders a report spec with Lit and Web Awesome Pro: answer first, with the chart previews when offered beside the title (at the header's end, their tops level with the title's) while they fit there, else wrapped below the answer, then the chart, the breakdown table and the source, in the spec's `locale` and `dir`. Set its `spec` property. Where the spec offers `Visualizations` and binds `selectChart`, the chart shown goes where they are, below the previews, so changes in chart height leave the previews in place; its `chart` property is the chart shown (by default, and for a kind the spec does not offer, the main one; a new spec starts at its main one unless its host sets `chart` with it).

- The previews (`preview.ts`): a toolbar beside the title, or above the chart when they do not fit beside it, of tiny SVG drawings of every chart the spec offers, in its order, each from the spec's numbers (the main one from the Chart) in the chart's colors, with no labels, axes or tooltips, a short name under each (`name`). There is no Table card: the breakdown table always stays below the chart. `table` remains in the public spec, request `chart` and state contracts, and table-only reports still show no chart until one is chosen. The chart shown is pressed (`aria-pressed`) and alone in the tab order; without a chart, none is pressed and the first chart preview is in the tab order; the arrow keys move between them in the report's direction, Home and End to the ends, and a click, Enter or Space shows one in place of the chart, at once, from the data the spec carries, with no network (~20 ms in Chromium), and fires `report-select-chart`. The chart asked for that does not fit has no preview: the Report's `notice` says why, under the subtitle. Six of them fit beside a title of 17rem in a report as wide as the Book's panel (about 47rem: cards of 4.25rem); on a row of their own they wrap on wide reports and scroll sideways on narrow ones (`max-width: 40rem`); drawings run from the inline start, so they mirror in right-to-left reports. The table's swatches follow the chart shown.

- The Source (`source.ts`) is one line under the table (`.source-line`): **Details** at its start, a button with `aria-expanded` and `aria-controls` and the rows' chevron, and the link (Open in Bkper, or the host's `link`) at its end, in the report's direction. Details start closed and open in place below that line (`.source-details`): the period, the query, when balances were read and the footer naming the Book. Opened, they stay open across specs, as rows do. A `calculated` label and note show above the line, never hidden (`.source-calculated`), in the app and in report files.
- The `Report`'s `notice`, when it has one (a comparison asked for that could not be made), shows under the subtitle (`.report-notice`, `role="note"`), in the app and in report files.
- Self-contained: no app state, no network, and only type imports from `report-shared/catalog` (its validation code is large; the server validates every spec), plus the tiny `report-shared/bidi`. It registers the Web Awesome charts and sparkline it uses; the page provides the Web Awesome theme and `@bkper/web-design` tokens. So the web app and a standalone report file can bundle it alone.
- `format.ts` formats the spec's decimal strings exactly with `Intl` (never through floats); `ReportFormat.plot` gives the numbers charts draw. Charts' tooltips show the exact amounts, name and amount each isolated. A share never shows as a signed zero: a share too small to show, other than zero, reads `<0.1%` in the locale's digits.
- `chart-config.ts` builds the Chart.js configuration of every chart kind, for `wa-bar-chart`, `wa-line-chart` and `wa-doughnut-chart`. Colors are the Bkper type color tokens (`--bkper-color-<color>-<low|medium|high>`, the palette of Bkper's charts), so they follow the light or dark theme; a donut and stacked parts shade items of one color from high to low (`shades`). Ranked bars of negative values go the other way from zero, in their type's color, with room past zero (`grace`) and a minimum length, so a tiny value, such as a small overdraft, still shows.
  - By month: `bar` (bars), `line` (a line), `area` (each series filled from zero, the net result's `line` series a line over them, on an axis from zero) and `stacked` (stacked bars, a shade per part, a line of the surface between parts). Lines and areas keep half a month from the chart's edges (`offset`), so the first and last months' labels show whole in either direction.
  - `compare`: horizontal bars in pairs, the previous period first, outlined (a light fill and a border), and this period solid, so they differ in more than color; the legend names both periods. A zero draws no bar.
  - `waterfall` (in the v1 catalog; reports no longer give one, so its tests read the recorded `client/test/report/waterfall-specs.json`): floating horizontal bars in `wa-bar-chart` (Chart.js `[start, end]` data, positions in display floats only; the exact amounts are in the tooltips). The start and end stand on zero, solid in the strong tone; a step up is solid, a step down outlined. A small Chart.js plugin of the config (`barLabelsPlugin`) writes each bar's value (`barLabels`) past its end, steps with their sign (`signedCompact`), in the ticks' font and color, and past its other end when it does not fit in the chart, so labels never cover the names.
  - `chartSwatches` gives the colors of the rows a chart draws as items or series of their own (ranked bars, donuts, pies, comparisons and stacked parts), the table's swatches.
- Several Answers (targets side by side) show together where the first is, in a row that wraps (`.answers`), each with its label. In charts by month, series of one type color get tones of their own (`seriesTones`: the first in its usual tone, the others lighter), so targets side by side stay apart; the legend names them.
- Values the renderer places next to texts (amounts, changes) are isolated with CSS (`unicode-bidi: isolate`) and inherit the report's direction; texts of the spec carry their own isolates.
- The breakdown is a plain table with disclosure buttons, not `wa-data-grid`: the grid would more than double the renderer's size (about 600 KB minified) and it would hide the row hover the chart follows. `wa-icon` fetches its SVGs, which a strict content security policy blocks, so the chevron is inline SVG.
- Rows open in place when the spec binds `expandRow`. Hovering or focusing a row, or else the row opened last, highlights it in the chart: its top-level item in a breakdown chart or a comparison, its series in a net result, the part it is in when parts are stacked, its steps in a bridge (a row that holds steps, such as Outgoing, also highlights the rest of them), or its months added to another chart by month; the rest fades. A row the chart does not draw (no amount in the period) highlights nothing. The table's swatches are the legend of the rows the chart draws.
- A series with `line` is drawn as a line over the bars of `wa-bar-chart` (Chart.js mixed datasets, no extra component). The table's `total` is a `tfoot` row.
- Events (`events.ts`), bubbling and composed: `report-expand-row` (`{ rowId, expanded }`), `report-select-chart` (`{ kind }`, the chart chosen from the previews) and `report-open-in-bkper` (`{ url }`, on a plain click only, cancelable: cancel it to navigate another way; a click that asks for a new tab or window opens one). In a Book whose last `bkper:host-ready` lists `navigate`, the web client cancels it and sends `bkper:navigate` with the query's page on the Book's origin (`AppState.openInBkper`): the Book opens its transactions of the query in place and keeps Report open beside them; else the link opens in a new tab. The link to Bkper shows only when the spec binds `openInBkper`; a host that cannot navigate sets `link` (`{ url, label }`) instead, a plain link in the Source.

`http://localhost:5207/dev/report.html` is a development-only gallery of recorded specs (`?only=<id>,…`, `?width=<css length>`; the `bkper_theme` cookie picks light or dark). `npx tsx scripts/generate-report-specs.ts` rebuilds those specs (`client/dev/specs/*.json`, which the renderer tests read) with the real report and spec builders from made-up Books shaped like recorded payloads: `scripts/fixtures/studio-book.ts`, a balanced design studio whose net result Report calculates, and the server test Book, whose net result is its combining group, with a refund that puts Food below zero. Rerun it when the report data or the spec changes. With Book ids it reads live Books, read-only, into `client/dev/specs/local/`, which Git ignores so real Book data is never committed.

## Report file

`format: "html"` returns one self-contained HTML file of the report, for the Bkper Agent, which shows a published HTML file in an `<iframe sandbox="allow-scripts">` whose `srcdoc` starts with its Content-Security-Policy (`default-src 'none'`, inline scripts and styles only; bkper-clients `packages/agent/client/src/file-views.ts`). So the file loads nothing: no network, fonts or icons.

- `npm run build:report-file` (`client/vite.report-file.config.ts`) bundles `client/src/report-file/` alone, the renderer with the Web Awesome theme and `@bkper/web-design` tokens, into one classic script and one stylesheet, written as `server/src/generated/report-file-bundle.ts` (Git and Prettier ignore it). The build fails if either holds text that would end its inline element. `postinstall`, `dev`, `build` and `check:generate` run it before anything imports the server; rerun it after changing the renderer while `npm run dev` runs.
- `buildReportFile(spec, link)` (`server/src/services/report-file.ts`) writes the document around that bundle, held in the Worker's memory: `lang` and `dir`, `<meta charset>`, the same policy, a `<title>` of the report's title and period, and the data (`ReportFileData`, `report-shared/report-file`) as a JSON script with `<`, U+2028 and U+2029 escaped. Nothing is bundled per request; `render` in `Server-Timing` includes it.
- The file cannot open Bkper in place, so the Source drops `openInBkper` and links to the same report in the Report app (the response's `url`, `source_open_in_report`). The file also carries the Book and the report's state (`open`, left out when the state does not fit); once the window around it says `bkper:host-ready` with `navigate` in `supports` and the Bkper `origin` (any web origin: the Agent checks the link again; as the Bkper Agent tells the files it shows, from the parent window only), a plain click on that link sends `bkper:navigate` to `<origin>/books/<bookId>/transactions?app=report&appState=<state>` instead (`followFileHost`), so the Book opens the report in the Report app in place of the Agent. The Agent passes it on only while the file's frame has focus, as it does after that click, and tells the file `bkper:host-ready` again when the Book starts accepting navigation after the file loaded. Until then, it stays a plain link that opens a new tab; only a click sends anything. The file follows the viewer's light or dark color scheme (`prefers-color-scheme`); rows open in place and charts show tooltips offline.
- The previews work offline in the file: choosing one changes nothing outside it, and its link and `bkper:navigate` then open the report as that chart (`chosenReport`: the state of `open.charts`, also as `&state=` on the plain link; the file's own link and state for its main chart).
- The bundle is ~357 KB and stays under 400 KB (a test); the Agent shows HTML files up to 1 MB, so report data has the rest.

It also checks that there is no Table preview, Tab reaches the toolbar even on table-only reports, arrow keys follow the report's direction, Home and End reach the ends, previews sit beside the title, level with it, in a report at least 760 px wide, and stay above the chart at the same position when switching (including a different-height monthly-to-round-chart regression), and the breakdown stays below it. Without files it writes one per recorded spec; files saved from the local Worker end with the live-reload script `bkper app dev` adds to HTML, which it leaves out. ## Web client

The app has one layout everywhere, in a Book's panel (`menuOpenMode: EXPANDED`, over the transaction list) or opened directly (`components/report-page/`): the report scrolls above an input fixed at the bottom, and morphs in place; notices and the suggestions (chips, when the input is empty) sit just above the input.

- The input matches the Book's transaction input measure for measure (bkper-clients `transaction-record-view.ts` and `transaction-record-css.ts`): a pill `wa-input` in a bar `3.75rem` high (padding medium above, small at the sides; the input padded 2x-small above) at the top of a footer `5.1875rem` high, with `--bkper-border`, the default placeholder and Web Awesome's clear button (`with-clear`, shown while there is text; it clears the request and keeps the focus). `styles.css` applies Bkper's density (`--wa-space-scale: 0.9`, `--wa-font-size-scale: 0.92` from 768px), as the Bkper page does, so the sizes match. Check it against the Book after changing either.
- The input shows, focused, in the app's first frame, and never moves: what sits above it grows upwards, and the report changes inside the scroll area. Enter asks at once (`enterkeyhint="send"`), Escape clears the request; while names of the Book show (see Completing names), Enter accepts only a highlighted name and Escape first dismisses them.
- With a Book in the URL there is no Book picker and no breadcrumb. Without one, the Book picker (or its loading or error) shows above a disabled input.
- `VisualViewportController` (`components/report-app/visual-viewport.ts`) sizes the app to the visual viewport, so on phones the input stays above the on-screen keyboard; `index.html` asks Chrome to resize the page for it (`interactive-widget=resizes-content`).
- In a Book, the report on screen keeps its state (see Report state) in the Book's URL: `bkper.yaml`'s menu URLs pass it as `&state=${app.state}`, and a missing or empty value, or the expression left unreplaced by older Bkper versions, is no state. A valid state opens its report by its text, in its language and with its chart (`Reports.openState`), over any `q`, and the input shows that text at once. Once the Book's `bkper:host-ready` lists `app-state`, each new report sends `bkper:app-state { state }` (empty when its state does not fit) and keeps it in the app's own URL; a report whose state the URL already has sends nothing. A chart chosen from the previews (`Reports.chooseChart`, from `report-select-chart`) is the report's state with that `chart`, sent the same way; the main chart again is the report's own state. A `bkper:app-url-changed` of another state shows that report; of the same Book without one, nothing changes. `BookHost` (`state/book-host.ts`) hears only the parent window on a Bkper origin (`bkper-host.ts`: production and development, and Bkper run locally only for the app run locally) and sends only to the origin of the last `bkper:host-ready`. Standalone, the app's URL keeps the same state (`?book=&q=&state=`), so a reload opens the report on screen, as the chart chosen.
- The report follows the Book (`Reports.follow`): `bkper.yaml`'s menu URLs pass the query the Book shows its transactions with as `&bookQuery=${transactions.query}`, which Bkper leaves unreplaced when the Book shows none; that expression, the legacy `${query}` and `{query}`, or an empty value is no query (`route.ts` alone reads it, `Route.bookQuery`, the query last followed). A `bkper:app-url-changed` whose query differs from it (`BookQueryChange`) asks `POST /report { query, language }` in the interface's language, so the report follows the groups and Accounts chosen in the Book's sidebar and its search, and shows it like any report: the same transition, its `text` in the input and in `q`, its state sent to the Book, and the chart chosen (or asked for) kept when the next report offers it (`Visualizations`), else its main one. The Book changed, so it replaces what was typed or on its way; any failure of a followed query (`query_not_a_report`, `mixed_targets`, a problem, Bkper failing) leaves the report, the input and the notices as they are, silently. A URL that repeats the query, such as the one the Book sends after `bkper:app-state`, never asks again, so a typed request stays until the Book's query really changes. When a URL changes both the state and the query (Back in the Book), the state wins: it is the report shown with that query. Opened with a query (in a Book, or standalone with `bookQuery` in the URL) and no valid `state` or `q`, the app shows its report; `openFirst` waits for it (`Reports.followsQuery`) and, when it has none, opens as with nothing asked.
- Embedded, the light or dark theme follows `bkper:theme-changed` through the first-paint theme script, and the text scale follows `bkper:font-scale-changed` (`host-font-scale.ts`, `--wa-font-size-scale`, 0.5–2), both only from the parent window.

Without a Book in the URL, the app shows the Book picker (`components/book-picker.ts`): the person's Books changed most recently (`lastUpdateMs`, sorted by the `Books` store), at most `RECENT_BOOKS` (8), and, when they have more, a field that finds any of them by every word typed, ignoring case and accents (`findBooks`); Enter opens the first. Its texts, the loading state and the errors of the `Books` store (string keys) come from the strings, in the interface's language and direction; Book names keep their own direction.

The Book page is one input, with no submit button, and the report above it. Its behavior lives in the `Reports` store (`state/reports.ts`), the input controller, which the unit tests cover:

- A request goes out `DEBOUNCE_MS` (250 ms) after the last keystroke once it has `MIN_WORDS` (2) words, counted with `Intl.Segmenter` so languages written without spaces count too; Enter asks at once. A newer request aborts the one in flight (`AbortController`), and an answer to any but the latest request is dropped (a sequence id).
- The last report stays on screen while the next is on its way, with a thin progress line under the input that appears only when the wait is felt; the page changes into the next report with a view transition scoped to the report's scroll area (`Element.startViewTransition` on `.scroll`), over the whole page where only document transitions exist, and without one otherwise or under reduced motion. The scroll area, not the report: its snapshot is never larger than the screen, while a whole report hundreds of rows tall, on a 2x screen, is larger than the snapshot the browser takes, so it was captured smaller and shown scaled up. Snapshots keep their own size from the top (`object-fit: none`) instead of the browser's default stretch to the transition's box. Scoped, the transition captures the next report once its chart has drawn at its size (`ReportView.chartDrawn`, a few frames at most): Web Awesome's charts draw a frame or more after the report updates (a new chart element after a timer and a frame), at first at the last chart's size, so the capture would otherwise hold a blank chart or the last one squeezed into the next one's box; over the whole page nothing draws until the capture, so it does not wait.
- Reports are remembered in memory per Book for `CACHE_MS` (60 s, `state/cache-window.ts`) from when they were asked, by request (whitespace runs as one space, case kept: it tells apart names of the Book written alike but for case) and the chart asked for with it (a state's), saved requests too; failures are forgotten, and so is everything on another Book. After a minute a request asks again (the report on screen stays until it answers), so relative periods advance; with the Worker's 60 s balances cache, a report can be up to two minutes behind the Book; an answer that arrives late shows but is not reused. The clock is `Date.now` (it runs through sleep; a clock that went back expires everything), injectable as `now` in `AppState` and `Reports`. The chart chosen for the report on screen (`chart`) holds that report, so another report shows its main chart in the same change. When the suggestions arrive, their reports are asked for by their texts, in the interface's language (`{ prompt, language }`, which the Worker builds with no AI), and remembered under their texts, so choosing or typing a suggestion shows it from memory; chosen after that memory, a chip asks the same way. The suggestions come from the Book's map and their reports' balances, which the Worker keeps for the same 60 s: the first request after a minute asks them again, once, in the background; the ones shown stay until new ones arrive, and stay without a notice when that fails (asked again a minute later), and their reports are fetched again.
- A Book opened with nothing asked (signing in on it, or choosing it, with no `q` and no valid `state` in the URL) opens its first report by itself, exactly as clicking that chip, so the same report, URL and Book state (`AppState.openFirst`): once the shelf's list settles, its first saved prompt (`openSavedPrompt`: one Bkper AI call, from memory within a minute), else, when the suggestions arrive, the first one (`Reports.choose`, by its text, with no AI). A shelf that fails leaves it to the suggestions; no suggestions, or a Book problem, open nothing. The person wins: anything asked of the Book first (`Reports.untouched`: typing, even a request cleared, Enter, a chip, a saved prompt, a state, a report of the Book's query shown), Back, Forward, a URL Bkper changes, or another Book cancel it; nothing opens by itself again until the app opens, or another Book is chosen. The input then shows the request selected, with the focus in it, so the first keystroke replaces it: `Reports.selectText` fires `select-text` (`SELECT_TEXT`), and the page selects the input's text once it shows it.
- Before the Book has saved prompts, suggestions show as chips (their texts only, like saved prompts) in the shelf over the input, including while viewing a report or typing, fading in when they arrive. Once saved prompts exist they take the suggestions' place. The report notices answer: `not_a_report` (a quiet hint; the last report stays) and `ai_allowance_exhausted`. Other failures show a short message from `shared/catalog/en.json`, never the error (`no_net_result` without a `problem` says to add a group that combines income and expenses); an error or suggestions with a `problem` show its message instead (see Agent links). One message shows at a time: a Book that cannot be read shows the API's reason (`book_not_found`, `forbidden`), else that its details did not load (`error_book_load`).
- `route.ts` alone keeps the request in the URL (`q`), replacing the entry as the person types; opening a URL with `q` runs it at once. It keeps the report's state (`state`) and the Book's query (`bookQuery`) the same way, and follows the app URLs Bkper sends (`follow`). Another Book drops all three.
- Completing names (`BookNames`, `state/book-names.ts`; the index in `report-shared/name-index`): `AppState` opens the Book's names with its reports once signed in, in the background (`GET /names`), never before first rendering. `complete(text, caret)` reads only memory: no request per keystroke. The names come from the Book's map, which the Worker keeps for `CACHE_MS`: on the reports' changes (typing), `refresh()` asks again once they are older than a minute, keeping the names known until new ones arrive (the index is rebuilt only when they changed) and when that fails (asked again a minute later); a Book that can no longer be read (`forbidden`, `unauthorized`, `book_not_found`) forgets them. Another Book starts over; session guards and abort signals drop late answers, even across A → B → A. `NameIndex` completes the end of the request at the caret, from a word boundary on, once it is 2 folded characters (`MIN_COMPLETION_LENGTH`), when the caret ends a word and is outside `#hashtags`: names that start with that text, or with a word that does (no fuzzy or in-word matches), ranked by the most of the text completed, then names that start with it, then the shortest, then Book order, at most `MAX_COMPLETIONS` (5). Each completion is `{ name, text, from, to }`: `text` (the Book's name, whitespace collapsed and trimmed) replaces `from`–`to` (the caret). It offers only what the Worker then reads as that name: never one character, of names written alike the one the Worker reads, not a name already written exactly, and each completion is checked with `matchNames` against the request it makes, so a name a longer one would swallow (Card after "credit" when the Book has Credit Card) is not offered. `server/test/services/prompt-names.test.ts` checks every completion of every prefix of every name in several contexts against `findPromptNames`.
- The input shows the completions as a list-autocomplete combobox (`components/report-page/name-completion.ts`, `NameCompletionController`; drawn by the page): a `wa-popup` listbox over the report, anchored to the top of the dock (`top-start`, never flipped), so it never covers the input, the saved shelf or a notice, measured like the Book's input suggestions (a Web Awesome dropdown's), each name in its own direction (`bdi`) with a localized Group or Account tag (`completion_group`, `completion_account`), each option as tall as a form control for touch. The `<input>` inside `wa-input` keeps the focus and is the combobox: `role`, `aria-autocomplete="list"`, `aria-expanded`, and, as the listbox lives in the page's shadow root, `ariaControlsElements` and `ariaActiveDescendantElement` (element references, which reach into a shadow-including ancestor; ids cannot). Nothing is highlighted at first. Tab (or a click or tap, which keep the focus and the on-screen keyboard) accepts the highlighted name, else the first; ↑/↓ browse, wrapping; Enter accepts only a highlighted name, else closes the list and runs the report; Escape dismisses the list, and only then clears the request. Accepting writes `applyCompletion` (`report-shared/name-index`) synchronously into the input: the name replaces only the text it completes, the rest of the request stays as typed, the caret goes after the name (and a space when the name ends the request), and `Reports.input` takes the new request, so the debounce asks for its report as for typing. Names show only once the person has typed in the request: one opened for them (a reload or state, the Book's query, a suggestion, a saved prompt, the first report) shows none on focus, on a click or when names arrive, until they type. After accepting or dismissing, nothing shows until the person types or moves the caret (arrow keys, Home, End, a click). Completions follow the caret, close when the input loses focus or its text changes elsewhere (a suggestion, a saved prompt, the clear button), and appear when names arrive while typing. While an input method composes (`compositionstart`–`compositionend`, `isComposing`, Safari's key code 229) nothing completes and keys are the input method's.

## Strings

`shared/catalog/en.json` holds every UI and report string: key → `{ text, role, context, placeholders? }`. Placeholders are named, `{name}`, and each is documented in `placeholders`; a test enforces both. Write `context` for a translator who sees nothing else: where the string appears, what it means in Bkper, and how short it must be.

`t(key, lang, params)` (`report-shared/strings`) reads a language added with `addLocale(lang, messages)` (a flat `key → text` map), then its base language (`pt-BR` → `pt`), then English; blank texts fall back too. Params fill placeholders verbatim, so format numbers and dates before passing them; a placeholder without a value stays visible. `textDirection(lang)` gives `rtl` for right-to-left languages (a test checks it against each language's script).

`shared/locales/{lang}.json` holds the strings of each of the 133 Bkper languages, checked and recorded by `npm run translate` and committed; never edit `en.json`, which is the catalog's English. A string added before it is translated is written in English into every locale, with no hash in `scripts/translate/sources.json`, so it shows in English and stays pending until its translations are written and recorded. How they load:

- The Worker imports all of them statically (`report-shared/locales`, `addAllLocales()` in `server/src/index.ts`), so reports and suggestions are written in any language.
- The browser loads only the interface's language, a chunk of its own (`report-shared/locale-loader`, `loadLocale`), through the `Strings` store (`client/src/state/strings.ts`): the interface shows in English at once and in the person's language when its strings arrive. Components write their texts in `strings.language`.
- A report file carries no strings: its spec has every text resolved in the report's language.

`npm run translate` (`scripts/translate.ts`) checks and records the texts written in `shared/locales/*.json`, with no Bkper AI: a coding agent translates a string itself and writes its text into every locale, following `scripts/translate/prompt.md` (the rules for meaning, glossary, placeholders, tone and clean values), each language's tone (`scripts/translate/tones.ts`) and the Bkper words the text uses (`scripts/translate/glossary.ts`), both copied from bkper-clients `packages/translations`. `npm run translate -- --dry-run` lists the pending texts (missing, or whose source changed) by key and language; write every one of them, then run `npm run translate`. It checks every selected text (`recordTexts` and `translationError`, `scripts/translate/translation.ts`: present, placeholders exactly as in English, Bkper kept, not empty, not quoted, no line breaks, no explanations), and only when all pass records the pending ones' source hashes in `scripts/translate/sources.json`; a missing or invalid text fails it, naming the key and language, and records nothing. It cannot tell a translation from a stale or English text that passes the checks, so record only texts you wrote for the current source. `--keys` and `--languages` narrow it. The hash covers each text's source (English, role, context, placeholders, glossary words, tone), so changing any of them makes the text pending again.

Calling Bkper AI is opt-in, never the default: `npm run translate -- --ai` translates the pending texts with a Bkper AI language model (`claude-sonnet` by default, the model of Bkper's own interface translations, with strict JSON output), with your `bkper auth token`, labelled `bkper-ai-source: report-translate`. Each call is one key and up to 44 languages (`--batch`; a strict answer for all 132 at once is more than the model accepts), with the key's text, role, context and placeholders, the tone and the glossary words, and `scripts/translate/prompt.md` as instructions; every text is checked before it is written; `--force` redoes the selected ones; up to 8 calls run at once (`--concurrency`), with retries. Use it only when the person asks for it.

Each run, in either mode, also writes `shared/locales/en.json` and the two loading modules (`shared/src/locales.ts`, `shared/src/locale-loader.ts`). After adding or changing a string, translate it, record it and review the new texts of a few languages; `shared/test/locales.test.ts` fails until every language has every key.

## Web Awesome Pro

The client depends on `@awesome.me/webawesome-pro`, pinned exactly, from `https://npm.webawesome.com/`. Import components and themes from `@awesome.me/webawesome-pro/dist/...`, never from the free `@awesome.me/webawesome` package. The Agent Skills under `.agents/skills/` are synced from the Pro package and include its Pro components, such as the charts and data grid.

The committed `.npmrc` contains only the registry and `${WA_TOKEN}`. Each developer uses their own token:

```bash
export WA_TOKEN="$(cat ~/.config/webawesome/token)"   # or your own token source
npm install
```

Never print, log or commit the token. Without it, `npm install` fails with `E401` from `npm.webawesome.com`.
